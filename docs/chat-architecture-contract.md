# MAOMAO 聊天子系统架构契约（第一阶段 · 第二步）

**状态：** 契约草案，供渐进式重构使用  
**建立日期：** 2026-10-29  
**范围：** 聊天详情、聊天列表、消息搜索、聊天扩展、记忆、线上/线下模式及相关跨页面读写入口  
**最新进度：** 已新增共享纯判断模块 `shared/js/phone/chat-message-policy.js`，供聊天详情与历史搜索共用；保留旧逻辑兜底，并登记到 PWA 预缓存。未修改 UI 样式、消息格式、存储 key 或用户数据。

> 本文区分“当前兼容契约”和“未来目标边界”。当前兼容契约必须先遵守；目标边界只指导后续小步迁移，不代表代码已经实现。

## 1. 目标与非目标

目标是建立稳定的聊天内部接口，减少修改一项功能时对其他功能的连带影响，并为后续抽离纯逻辑、统一数据读写和回归测试提供依据。

本阶段不更换框架、不改成 SPA、不引入新运行时依赖、不重写聊天 UI、不变更消息存储格式，也不删除历史兼容分支。项目当前使用原生 HTML/CSS/JavaScript、多页面跳转和 IIFE 全局命名空间；后续重构应先适配这套约定。

## 2. 当前职责地图

- **页面与界面**：聊天列表、聊天详情、消息搜索、对话设置、通话、线下剧情等各自保留页面职责。
- **聊天流程协调**：聊天详情页当前的 sendMsg 负责输入校验、并发保护、上下文拼接、流式请求、回复后处理、群聊后续发言与消息落库。
- **消息展示**：详情页负责将多种历史消息对象转换为 DOM；线上页面隐藏 mode=date 和 silent 消息。历史搜索复用 `ChatMessagePolicy` 的过滤判断；DOM 渲染和索引协调仍留在页面内。
- **AI 流式请求**：PhoneStream 负责流式 HTTP/SSE、超时、增量渲染回调和失败时保留已接收文本。聊天详情与赴约叙事页已复用它。
- **非流式 AI 请求**：PhoneAPI 提供非流式请求、JSON 清洗和日志能力；聊天记忆总结等已有流程仍存在独立请求实现。
- **存储**：PhoneStorage 提供聊天历史和记忆的读写接口，但部分旧页面仍直接访问 localStorage。
- **记忆**：详情页含权重记忆注入和总结协调；MemoryRecall 提供清洗、去重/强化、记忆保存和旧聊天检索工具；记忆空间页面也会读写同一批记忆数据。
- **扩展互动**：chat-extras.js 依赖详情页暴露的函数与全局状态；红包/转账、心声、虚拟图片、通话、亲属卡等特殊标记与消息对象共同构成现有聊天行为。
- **共享消息策略（渐进迁移中）**：`shared/js/phone/chat-message-policy.js` 提供纯函数，用于线上时间线隐藏规则、搜索索引过滤、错误消息识别、消息文本字段读取、用户消息识别、推理标签清理、`[记住:…]` 标记提取和回复旁白/气泡分段；另提供 `cleanupReplyPreservingBlocks`，在现有页面传入的 `applyAICleanup` 回调前后保护 `<think>` 与 `<narratage>` 块。模块自身不直接操作 DOM 或存储，用户自定义清洗规则仍由原页面函数执行。
- **发送选项归一化（第一步已拆）**：`shared/js/phone/chat-send-policy.js` 将 `sendMsg(opts)` 起始处的选项读取、布尔化、文本 trim 和自动接话深度下限处理集中为纯函数 `ChatSendPolicy.normalizeOptions`。它不检查角色拉黑状态、不获取 API 配置，也不处理请求或存储；发送控制流程仍由原页面协调。

## 3. 当前兼容契约

### 3.1 会话身份

1. 个人会话以现有角色 ID 作为会话 ID；群聊以现有群 ID 作为会话 ID。
2. 当前详情页使用群 ID 的 g 前缀识别群聊，这是现存隐式约定。在单独设计并迁移前，不得更改 ID 规则或批量重写存档。
3. 与角色直接相关的长期记忆仍以角色 ID 隔离；不得将群聊历史、角色个人历史或不同角色的记忆混写。
4. URL 查询参数中的 id、模式参数及返回路径属于外部页面入口契约。迁移时须保留既有链接可用性。

### 3.2 消息对象

历史消息是可扩展对象，不能简化为只有纯文本的固定结构。常见基础形态为 role、text、time；兼容读取需处理历史数据的 content 字段，并保留未知的扩展字段。

已在当前源码中出现或被当前页面使用的字段包括：

| 字段 | 当前兼容含义 |
|---|---|
| role | 常见值包括 user、assistant、sent、received；错误消息使用 system_error，部分消息也使用 isError 标记 |
| text / content | 消息文本的主字段；旧数据和不同上下文中会使用其中任意一个 |
| time / timestamp | 消息时间；历史消息可能缺失或使用旧形式，当前详情页会为部分旧消息补齐时间与 mid |
| mid | 单条消息稳定标识，用于编辑、复制、转发、删除和重生成等操作 |
| type | 消息类型扩展，例如 image、sticker、call、text、forwarded 及其他互动类型；不得只允许纯文本 |
| img / desc | 图片或贴纸等富消息可能使用的内容字段 |
| mode / scene | mode=date 表示赴约叙事消息；scene 可记录剧情场景 |
| silent | 隐藏的上下文指令或不直接显示为普通气泡的消息 |
| name / memberId | 群聊中用于标识发言成员及显示名字 |
| isError | 错误消息的兼容标记 |

以上为兼容观察清单，不是要求所有消息都必须具备所有字段。读取时应容忍缺字段；写入新消息时才按对应消息类型填充必要字段。任何标准化函数必须保留未识别字段，避免删除旧版本数据。

### 3.3 消息可见性与索引

1. 线上聊天详情不显示 mode=date 的赴约剧情消息，也不显示 silent 消息，但历史数据本身继续保留。
2. 聊天搜索、跳转高亮与详情页渲染必须采用一致的过滤和排序规则。过滤后重新编号时，不能误把可见索引当成原始历史数组索引。
3. 错误消息（role=system_error 或 isError）须继续使用现有的错误展示/搜索排除行为。
4. 重构应逐步将单条操作优先绑定到 mid；在搜索和高亮尚依赖数组索引的现状下，不能未经回归验证就改变索引规则。

### 3.4 存储接口与旧 key

现有主要存储约定：

- 聊天历史：chat_history_<conversationId>
- 长期记忆：chat_memories_<roleId>
- 群列表：phone_groups
- API 配置镜像：api_settings
- 记忆总结配置：chat_summary_auto_<roleId>、chat_summary_interval_<roleId>、chat_last_summary_<roleId>、chat_summary_processed_<roleId>
- 短行程状态与线上/线下模式：chat_journey_state_<roleId>、chat_mode_<roleId>
- 通话返回结果：sessionStorage 中的 call_result_<id>

PhoneStorage 当前读取聊天历史时优先读取 chat_history_<id>，不存在时再尝试 phone_data_v2 中的旧副本；保存聊天历史时先写 chat_history_<id>，成功后清理 phone_data_v2 中完全重复的聊天副本。因此不能照搬旧注释中“聊天历史始终双写”的说法，应以实际方法行为为准。

迁移规则：

1. 新增或迁移的聊天历史写入优先走 PhoneStorage，而非新增裸 localStorage 访问。
2. 旧页面中的直接读写与 fallback 暂时保留；按调用方逐一迁移，确认回归后再讨论是否删除。
3. 每次保存必须保留当前的角色/群会话作用域；写入失败不能伪装成成功。
4. 不在本阶段改变 key 名、清除旧 key、合并群与个人历史，或对既有消息做破坏性批量转换。

### 3.5 AI 请求与错误语义

1. 主聊天流式请求通过 PhoneStream.chat。其约定是返回包含 ok、fullText、error 的结果，并将 HTTP、网络、超时和流内错误作为结果描述；已接收的部分文本需要保留。
2. PhoneAPI 用于非流式/JSON 任务。它与 PhoneStream 的调用语义不同，不应为了“统一”而把所有请求硬塞进同一种接口。
3. 当前一些记忆总结、短行程消息生成等场景仍有独立 fetch。未来统一请求入口前，需要按流式聊天、非流式结构化任务、记忆总结与线下剧情分别登记参数、超时、计费日志和失败处理。
4. API 配置目前由 api_profiles_v1 / api_active_profile 与 api_settings 镜像共同维持兼容。聊天重构不得重置 API 配置，也不得把密钥写入日志或新增调试输出。
5. API 失败不应删除用户已发送的消息，也不应丢弃已收到的部分 AI 回复；错误提示与日志记录按现有可见行为保留。

### 3.6 记忆

1. 长期记忆继续按角色 ID 隔离，不将不同角色的记忆合并。
2. 现有记忆包含分类、重要度、状态、创建/强化时间、强化次数和来源等字段；fixed、confirmed、pending 等状态含义不得因拆文件丢失。
3. AI 回复中的 [记住:内容] 标记会被剥离出可见回复并交给记忆逻辑处理；标记不可作为普通气泡意外显示。
4. 现有权重、半衰期、条目数量上限、上下文字符预算、总结开关和总结进度都属于行为契约。第一轮拆分不调整算法参数或触发条件。
5. MemoryRecall 与详情页内部的记忆/总结实现职责并不完全相同；不能假定它们已经是同一套记忆服务，也不能直接用 phone_context.js 替换聊天详情页当前的人设/世界书/记忆上下文。

### 3.7 扩展模块的当前接口

chat-extras.js 当前依赖详情页中的 loadMessages、saveMessages、appendMessageToDOM、sendMsg、showToast、currentCharacter 和 chatMessages。它还会直接读写部分 localStorage，并处理互动面板、静默指令、图片/语音消息、通话结果及转账等功能。

在聊天服务接口完成前，这些全局函数视为兼容入口：保持现有名字和大致行为，不可只移动或重命名函数而不迁移调用点。后续由稳定的 ChatBridge/ChatService 门面逐步承接，然后让扩展模块一类一类改接。

## 4. 目标职责边界（尚未实施）

渐进式目标，而非一次性重写：

1. **Chat UI**：DOM 渲染、输入控件、滚动、消息动作面板与可见提示。
2. **Chat Controller / Service**：发送流程、并发锁、重生成、群聊流程、状态协调。
3. **Message Policy**：消息标准化、可见性规则、回复清洗、特殊标记解析与动作消息生成。
4. **Context Builder**：统一主聊天的上下文组装策略；保留近期历史、角色/群聊差异、世界书、记忆检索、token/字符预算及过滤顺序。
5. **Chat Repository**：为 PhoneStorage 提供聊天域门面，接管读取、追加、更新、删除和保存结果；短期内仍兼容旧 key 与旧消息格式。
6. **AI Gateway**：根据任务类型适配 PhoneStream 或 PhoneAPI，明确区分流式与非流式任务。
7. **Memory Service**：逐步协调记忆读取、强化、检索、注入与总结，但不在首次抽离中改变记忆策略。
8. **外部适配器**：为聊天扩展、搜索、线下模式、通话、钱包和论坛分享提供明确的调用边界。

已将可见性/搜索规则、推理文本清理、记忆标记提取、旁白与气泡解析及保护式回复清洗抽离为共享纯函数。另新增 `ChatSendPolicy.normalizeOptions`，让 `sendMsg` 使用共享函数归一化选项，同时保留原地回退代码。此次未迁移拉黑判断、并发锁、群聊可发言判断、API 配置、上下文拼接、流式请求或消息落库。接下来先补足发送前校验的自动测试与真实页面验收，再决定是否拆动更深的发送协调流程。

## 6. 重构前必须建立的回归基线

在开始移动代码之前，需要在浏览器/手机中至少核验：

1. 私聊文本发送、连续发送与重复点击保护。
2. 流式回复正常完成、空回复、HTTP 失败、断网/超时与部分回复保留。
3. 重新生成、指定消息重生成、编辑/删除/复制/转发、按 mid 定位。
4. 群聊成员选择、成员禁言/活跃时段、自动接话轮数、群私聊卡片和群互动。
5. 图片/贴纸、虚拟图片、心声、通话卡、红包/转账、亲属卡等扩展消息。
6. 静默指令不作为普通气泡显示，但依然按原逻辑进入适当的 AI 上下文。
7. mode=date 消息只在赴约叙事中显示；线上列表/详情/搜索仍保持现有过滤和索引一致性。
8. 记忆标记剥离、记忆去重/强化、固定与待确认状态、历史检索、总结确认/失败/进度记录。
9. 多角色间聊天与记忆不串数据；群 ID 与个人角色 ID 不互相覆盖。
10. 钱包、通话、论坛分享及线下模式写入的消息能在相关会话中按现有规则显示。
11. API 多配置切换后，主聊天、总结和线下模式仍读取正确的当前配置。
12. 本地存储写满/写入失败时，页面给出合理提示，且不误报保存成功。
13. 页面刷新、返回、重新进入后，历史消息与会话状态不丢失。
14. 在至少一个桌面浏览器和一台手机浏览器/PWA 上完成关键路径验证。

当前 package.json 的 lint 脚本只是打印“Lint passed”，并不构成真实静态检查或测试。每个阶段需记录实际运行过哪些命令、手测了哪些路径，不能用该输出代替端到端验收。

## 7. 后续迁移顺序与验收标准

### 第 1 批：纯逻辑抽离
- 只抽离消息清洗、可见性判断、特殊标记解析等没有 DOM 副作用的逻辑。
- 输入输出不变；先加兼容测试样例，再让页面调用新模块。
- 验收：已有消息渲染结果与标记处理一致；不改变数据内容、API 请求次数与上下文行为。

### 第 2 批：建立聊天门面
- 建立稳定 ChatBridge/ChatService 入口，为现有 loadMessages/saveMessages/sendMsg 等接口保留兼容包装。
- 扩展模块先改接门面，暂不要求所有跨页面调用方一次迁完。
- 验收：加号互动、静默指令、重生成和消息操作正常；既有全局入口没有提前消失。

### 第 3 批：迁移跨页面写入者
- 每次只迁移一类调用方（先低风险入口，再钱包/通话/线下模式等）。
- 所有写入走统一门面，保留原始读旧数据的能力。
- 验收：各入口写入内容与原先相同，消息显示规则不变，不出现重复或串角色。

### 第 4 批：上下文与请求路径收敛
- 把主聊天上下文组装从页面协调代码中逐步独立出来；先复用现有规则，不改变提示词顺序或长度预算。
- 再按任务类型统一请求配置、日志和错误处理。
- 验收：同等输入下请求消息结构、流式显示、记忆注入及失败语义保持一致。

### 第 5 批：记忆服务边界
- 协调详情页权重记忆与 MemoryRecall 的职责，避免出现双写/双算法，但先盘清两者真实调用链。
- 验收：条目数、状态、权重排序、强化次数、总结进度与旧数据一致。

## 8. 本阶段明确不做的事情

- 不删除旧页面或聊天功能。
- 不修改消息字段、角色 ID、群 ID、存储 key 或 URL 参数。
- 不调整记忆算法、上下文预算、总结触发频率和模型参数。
- 不在同一批次重构 UI、请求层和存储层。
- 不把“文件变少/目录变整齐”当成唯一成功标准；成功标准是边界清楚、行为不变、可验证并可回退。
