# MAOMAO 应用外壳迁移方案

> 状态：架构审计与迁移边界已确认；尚未改动现有生产页面。
> 分支：`feat/app-shell-migration-v2`
> 基线：从当前 `main` 分支创建。
> 原则：先建立可验证的小步迁移，不做全站推倒重写。

## 1. 为什么要改

MAOMAO 当前是原生 HTML/CSS/JS 的多页面应用（MPA）。每个主要功能有独立 HTML；桌面图标通过 `data-href` 导航，页面之间通常使用 `window.location.href` 整页跳转。

这种结构的主要问题不是“HTML 文件多”本身，而是每次切换页面都会重新经历文档导航、页面脚本执行、页面级初始化与数据恢复。对于聊天详情这样体量较大的页面，重新进入时成本尤其明显。浏览器缓存只能减少网络传输，不能消除每次导航后的 JavaScript 执行和初始化工作。

**目标不是把几十个 HTML 粗暴塞进一个文件，而是把 MAOMAO 逐步演进为：一个持续运行的手机外壳 + 按需加载、可保留状态的应用模块。**

## 2. 参考项目审计

### Miya 小手机（优先参考）

仓库：`Bella0960/mingruis-miya`（README 所指上游为 `lixooo00-lab/mingruis-miya`）

已核对：
- `index.html` 是统一主入口，承载启动、桌面和手机外壳。
- `js2/miya-lazy-boot.js` 定义应用资源组，公开 `miyaLazyEnsureApp(appId)` 等按需加载入口。
- 非聊天应用可按组加载 CSS/JS；加载结果和 Promise 会被记录，避免同一模块重复加载。
- 页面完成后在空闲时分批预加载其他应用组。
- `sw.js` 的预缓存清单保持较小；HTML/CSS/JS 走网络优先并回退缓存。

可借鉴：统一外壳、应用注册表、模块级懒加载、加载去重、空闲预加载。
不照搬：具体视觉结构、所有资源清单、其全部性能策略。Miya 主入口仍加载了不少全局 CSS，不能把“单入口”直接等同于“首屏一定轻”。

### AI Virtual Phone

仓库：`Bella0960/ai-virtual-phone123`

已核对：
- Next.js 15 / React 19。
- `app/page.tsx` 进入统一 `MainApp`。
- `components/main-app.tsx` 先初始化本地 KV 数据、准备首屏主题，再进入 `DesktopShell`。

## 3. MAOMAO 当前约束（迁移时不可破坏）

- 原生 HTML/CSS/JS 与 Vite 多页构建是当前基础；本轮不引入 React/Vue，也不先改构建链。
- `index.html` 是手机桌面入口，`desktop/js/script.js` 与桌面内联脚本承担桌面行为。
- `shared/js/nav.js` 当前生成跨页导航。
- `chat/chat/chat-detail.html` 是核心聊天页面，代码体量大，不能作为第一批整体迁移对象。
- 角色隔离与旧数据兼容很重要：`phone_current_contact`、`phone_data_v2`、`ai_custom_characters`、`chat_history_<id>`、`api_settings` 等现有存储格式保持不变。
- 所有角色数据隔离规则、API 请求参数、记忆注入策略、聊天渲染和消息发送行为均保持不变。
- 页面直达 URL、浏览器返回/前进、刷新恢复和桌面 PWA 入口必须继续工作。
- 旧页面继续作为兼容入口；迁移完成前不得批量删除或重命名旧 HTML。

### 需要先澄清的缓存事实

`CLAUDE.md` 中关于 Service Worker 注册状态的说明与当前检索到的 `index.html` 注册代码、`sw.js` 的版本状态存在不一致。迁移开始前应以分支实际源码和浏览器实测为准，先厘清真实注册行为；不把“加大预缓存”当作默认提速手段。

## 4. 目标结构

统一运行外壳负责：
1. 桌面、状态栏、全局导航与应用视图容器。
2. 当前路由、返回栈、浏览器 History 同步与深链接。
3. 全局角色上下文与应用生命周期协调。
4. 统一加载状态、错误回退和页面性能计时。

应用模块采用明确生命周期：

```js
{
  id: 'chat',
  load: () => import('./apps/chat/index.js'),
  mount(root, context) {},
  activate(context) {},
  deactivate(context) {},
  dispose() {}
}
```

上面是目标接口草案，不是已经写入项目的运行时代码。

关键原则：
- **按需加载**：用户首次打开某应用时加载其 JS/CSS；同一模块只加载一次。
- **状态保留**：暂时离开的应用默认停用/隐藏，不立即销毁；内存压力或明确退出时才 dispose。
- **单实例**：聊天模块不能因切换页面而反复注册定时器、监听器或重新读取整份历史。
- **数据仍以现有 PhoneStorage/localStorage 契约为准**：外壳不另造一套平行数据源。
- **模块隔离**：新模块必须有自己的根节点、生命周期和清理函数；不能把多个旧 HTML 的全局脚本直接堆到同一 document，造成重复 ID、全局变量冲突和重复事件监听。
- **分阶段兼容**：未迁移页面仍可经旧 URL 独立打开；已迁移页面可由外壳接管。
- **兼容层可暂用 iframe，但不作为最终模块形态**：当前旧页面各自有大量全局脚本、重复 DOM id 和页面级 CSS。为了先建立一个不整页跳转的统一外壳，未迁移页面由同源 iframe 作为隔离适配器承载；外壳只保留一个顶层文档，应用帧首次打开后可隐藏复用，所有帧共享同源 localStorage/IndexedDB。iframe 的 JS 全局仍然隔离，因此它只是迁移桥，不是“所有应用最终都放 iframe”。新迁移的应用应实现原生模块生命周期，直接挂载到统一外壳。

## 5. 分阶段实施

### Phase 0 — 建立真实基线（当前阶段）

- 明确 main 的提交基线与生产版本对应关系。
- 审核首屏加载链、页面脚本数量与执行重活。
- 在同一手机、同一网络条件下测量：首次打开桌面、二次打开、桌面→聊天、聊天→设置、返回聊天。
- 分开记录网络等待、资源下载、脚本执行、DOM 渲染、聊天历史渲染时间。
- 将结果作为迁移前基线；没有测量前不设虚假的“提速百分比”。

### Phase 1 — 统一外壳接管入口（已进入首轮实现）

- 保留现有 `index.html` 作为唯一顶层手机文档和桌面；在 `.phone-screen` 内加入统一 App Host。
- 桌面图标点击由外壳接管，应用打开时不再把顶层 `index.html` 整页导航到目标 HTML。
- 旧 HTML 页面暂由同源 iframe 适配器隔离承载；每个目标路由首次打开时创建帧，切换应用时隐藏并复用，返回/前进通过顶层 History 路由恢复。
- 旧页面内部的普通同源链接由适配器转交外壳；旧脚本直接修改 `window.location` 的行为仍留在 iframe 内，并由加载事件同步顶层路由。
- Service Worker 安装预缓存从“预装一批应用页和图片”收敛到启动必需的手机外壳资源；应用页与静态资源在首次访问时再缓存。
- 已加入旧页面桥接测试与外壳生命周期测试；必须再通过生产构建和浏览器实测，才能进入下一阶段。

### Phase 1.5 — 设置应用原生模块迁移（当前实现）

- `settings/settings.html` 作为旧页面兼容入口继续保留；桌面打开该路径时由路由表映射到原生 `settings` 模块，不创建设置 iframe。
- `apps/settings/settings-module.js` 在首次打开时按需读取原设置 HTML、原设置 CSS、`settings/js/settings.js` 与 `settings/js/backup.js`；把真实页面 DOM 放进该应用自己的 Shadow DOM。
- 通过模块级 Document Facade 将原脚本的 `getElementById/createElement/body/documentElement` 查询限定在设置 Shadow DOM，避免设置页 ID、样式和全局脚本与桌面及其他模块冲突。
- 原 API 多方案、模型拉取/测试、备份/恢复、深色模式、状态栏设置和聊天语言设置逻辑继续复用；现有存储键与数据结构不迁移。
- 设置应用的外观、字体、音效等独立子页暂留在兼容层；设置→子页→浏览器返回可以回到已挂载的设置视图。
- 增加了浏览器级测试：验证设置页面由 Shadow DOM 原生模块承载、无设置 iframe、API 面板可开关、深色设置写入原存储键，以及进入兼容子页后可返回设置。
- 尚未在真实浏览器/手机上执行该测试；CI 安装 Chromium 后会运行构建和测试。

### Phase 2 — 核心页面渐进迁移

- 先迁移桌面周边轻页面，再处理设置。
- 聊天列表与聊天详情分开评估；聊天详情最后迁移。
- 对聊天采用单实例持有策略，保留滚动位置、草稿、当前角色与会话状态。
- 迁移时只改变页面承载方式，不顺便重写 AI 请求、记忆、消息存储或聊天 UI。

### Phase 3 — 其他应用迁移

- 以应用为单位接入注册表与生命周期。
- 大体量模块（游戏、阅读、深海等）保持真正按需加载。
- 共享依赖抽到明确的公共模块，不重复执行初始化。

### Phase 4 — 性能与 PWA 收口

- 根据实测调整 Service Worker 的资源策略，避免超大安装预缓存拖慢首次可用。
- 验证不同浏览器首次打开、二次打开、清缓存后打开、离线回退。
- 生产域名访问权限与浏览器性能分开验收；不同浏览器的 localStorage 本来就是独立的，不能把数据不同步误判为链接不可访问。

## 6. 验收门槛

每次迁移至少满足：

1. 聊天发送、流式回复、图片/语音等现有消息能力不回归。
2. 角色 A/B 数据严格隔离；切换角色不串历史、记忆、世界书或配置。
3. 原有 localStorage key 与旧数据迁移行为不变。
4. 直接打开旧 URL、刷新、浏览器返回/前进均正常。
5. API Key 不进入 URL、日志或新建的共享状态。
6. 已加载模块不会重复注册全局监听器、轮询和定时任务。
7. 新增性能测试覆盖启动与应用切换；性能预算基于真实基线确定。
8. 现有测试继续通过：`npm run test:chat:contract`、`npm run test:detective:unlock`、`npm run perf:gate`。

## 7. 当前决策

- **采用**：Miya 的单一外壳 + 按需应用加载思路。
- **借鉴**：AI Virtual Phone 的统一运行时与应用状态边界。
- **暂不采用**：全站 React/Next.js 重写、一次性合并全部 HTML、批量改写 localStorage、把所有应用静态导入首屏。
- **当前代码状态**：在 `feat/app-shell-migration-v2` 独立分支中，现有 `index.html` 已接入统一 Host；旧页面桥接与原生模块运行时已连接；设置主页面已完成第一版 Shadow DOM 原生模块迁移，设置子页面仍由兼容层承载；Service Worker 已收敛为轻量外壳预缓存。聊天业务、设置原 HTML/JS 和存储键没有被重写；尚未部署到生产。自动化测试、CI 构建和真机实测待验证。
