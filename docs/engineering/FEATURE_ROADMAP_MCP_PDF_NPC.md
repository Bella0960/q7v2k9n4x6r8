# MAOMAO 功能愿望路线图：MCP、PDF 单词导入与 NPC 主动交友

**状态：PLANNED（规划已登记，尚未实现）**  
**登记日期：2026-11-08**  
**目标：** 把用户提出的三项长期愿望纳入 MAOMAO 现有产品和技术架构，按独立、可验收的小阶段逐步实现。

> 本文是产品与技术路线图，不代表功能已经开发、部署或可在当前版本使用。所有实现均应在独立分支完成，通过 Draft PR 审查；未经明确批准，不合并到 `main`、不部署生产 Worker、不生成 APK。

---

## 总体原则

1. 延续 MAOMAO 现有原生 HTML/CSS/JavaScript 多页面架构，不迁移到 React/Vue，不另起一套手机应用。
2. 能复用现有 `PhoneAPI`、`PhoneStorage`、CharacterRepository、书架 IndexedDB、通讯录和聊天模块时优先复用；新数据域必须清楚隔离。
3. 保留已有角色 ID、聊天历史、书籍、阅读进度、评论、用户资料和备份数据。不为了新功能清空或重写旧数据。
4. AI 生成内容和第三方 MCP 工具结果都属于不可信输入；必须进行 schema 校验、转义、权限检查和错误隔离。
5. 先做能在手机上实际使用、能回归验证的小闭环，不以增加页面或按钮数量代替完成度。
6. UI 遵循 MAOMAO 黑白灰视觉规范；不引入渐变、紫蓝粉色强调色、Emoji 图标或不必要的品牌字样。

## MCP-001：MCP 外部工具连接中心

### 用户目标

在小手机的设置中管理 MCP 服务，让 MAOMAO 的 AI 在用户明确授权后使用外部工具。MCP 是连接模型与外部工具/数据源的一种标准协议，不是新的聊天模型，也不是 PDF 或 NPC 功能的前置依赖。

### 当前基线（已检查）

- 项目使用原生 HTML/CSS/JavaScript 多页面架构。
- `shared/js/phone/phone_api.js` 暴露统一 `PhoneAPI`；当前主要提供 OpenAI-compatible Chat Completions、JSON 请求和图片生成。
- 当前 Cloudflare 交付以静态网站资源为主，不能假设已有可保存 MCP 密钥的安全后端。
- 当前主分支代码检索未发现已接入的 MCP client/server 模块。

### 实施阶段

**MCP-001A — 连接管理与只读能力探测**
- 设置页增加独立 MCP 连接中心。
- 支持添加、编辑、启用、断开、删除服务配置，并展示连接状态。
- 第一阶段只实现浏览器能够安全使用的远程 HTTP 连接方式；不声称浏览器页面可以直接启动本地 stdio 服务。
- 成功连接后读取服务能力与工具清单，只展示服务名称、工具名称、说明和参数 schema，不自动执行。
- 对网络失败、超时、协议不兼容、授权失败分别提供明确状态。

**MCP-001B — 权限与安全调用**
- 服务级、工具级单独授权；默认关闭。
- 只读工具可单独授权；写入、发送、删除、发布、交易等有外部影响的工具必须逐次展示动作并取得用户确认。
- 增加调用超时、并发限制、错误隔离、调用历史和敏感字段脱敏。
- 工具结果作为不可信数据处理，不允许其覆盖系统指令、注入脚本或自行扩大权限。

**MCP-001C — 与现有 AI 运行时集成**
- 在不改变普通聊天默认行为的前提下，把已授权工具描述提供给 AI 编排层。
- 工具权限按当前用户、角色和场景隔离；角色切换不得继承不相关权限。
- 支持立即暂停连接、撤销授权与清除本机非敏感连接元数据。

### 安全边界

- 不将访问令牌、密码或密钥明文写入普通 localStorage、聊天历史、备份或 API 日志。
- 若静态客户端无法安全持久化凭据，必须先提供经审查的服务端凭据代理/后端方案；在此之前只做连接管理和能力探测，不宣称完整持久化连接已完成。
- 不自动连接未知服务、不自动执行服务端提供的工具。
- 不把 MAOMAO 改造成 MCP server，也不替换 PhoneAPI。

### 验收

- 可新增、编辑、探测、断开和删除服务。
- 能展示服务提供的工具和参数 schema。
- 未授权工具无法执行；拒绝授权后没有后台调用。
- 密钥不出现在 localStorage、聊天记录、备份和日志。
- 连接失败和工具失败不会阻断正常聊天。
- 现有聊天、主动消息和图片生成回归通过。

## LIB-001：PDF 识别并导入单词本

### 用户目标

用户选择一份 PDF 后，MAOMAO 能提取英文词汇，保留页码和上下文，经过预览、筛选和去重，再批量保存到单词本。

### 当前基线（已检查）

- `library/library.html` 的「导入本地书籍」目前接受 `.txt` 和 `.epub`，没有 PDF 文件解析流程。
- 当前阅读数据位于 IndexedDB `maomao-reading-library`，包含 `books` 与 `comments`。
- Vite 静态资源白名单包含 `.pdf`，但这不代表当前应用已经能解析 PDF。
- 当前主分支代码检索未发现已接入 PDF.js 或 PDF 词汇提取管线。

### 实施阶段

**LIB-001A — PDF 文本提取**
- 从书架或独立单词本入口选择 PDF。
- 优先提取 PDF 内嵌文本，保留页码和段落上下文。
- 支持进度、取消、重试、加密文件/损坏文件/超大文件错误提示。
- 不把整份 PDF 自动发送给 AI。

**LIB-001B — 词汇候选与人工确认**
- 从提取文本中识别英文词汇和基本词形。
- 过滤页码、目录、页眉页脚、明显 OCR 噪声及常见功能词。
- 允许搜索、选择、取消选择、修改单词和合并重复项。
- 同一单词在不同页面出现时，合并来源页码与有代表性的上下文。
- 候选列表确认后才写入单词本，不自动无差别收录整本 PDF 的所有词。

**LIB-001C — 扫描版 PDF 的 OCR**
- 对没有可选中文字的扫描版 PDF 提供 OCR 路径。
- 明确展示 OCR 识别质量；无法识别时要明确报错，不得显示虚假的成功状态。
- OCR 可以独立于普通文本 PDF 导入先后交付。

**LIB-001D — 释义与学习信息**
- 可选使用用户已配置的 AI 服务补充中文释义、词性、音标、常见搭配和例句。
- 未配置 AI 时仍可完成词汇提取和人工补充。
- 若使用外部 AI/OCR 服务，操作前明确说明会发送哪些文本内容。

### 数据与备份

- 单词本使用独立数据域，不与阅读书籍、段落评论、角色聊天记录混用。
- 词条至少包含：`word`、`lemma`、`meaning`、`partOfSpeech`、`phonetic`、`example`、`sourceBook`、`page`、`context`、`createdAt`、`updatedAt`、`reviewState`。
- 新增 IndexedDB 数据库/store 必须登记到 `settings/js/backup.js` 的备份与恢复清单，并增加 round-trip 测试。
- 重复导入同一 PDF 不得重复创建词条；备份恢复不能丢失来源信息。
- 原书架数据、阅读进度和评论必须保持不变。

### 验收

- 可导入普通文字 PDF 并显示页码来源。
- 可预览、筛选、编辑、去重后再导入。
- 重复导入不会重复增加词条。
- 解析错误、加密 PDF、无英文内容、超大文件、OCR 失败和存储空间不足有明确处理。
- 刷新、重开和整机备份恢复后词条仍在。
- 书架 TXT/EPUB 导入和现有阅读流程回归通过。

## NPC-001：NPC 自动生成并主动发送好友申请

### 用户目标

NPC 不再只是主角色档案中的人物介绍，而能在合理的剧情/生活情境中出现，向用户发送 MAOMAO 好友申请。用户接受后，NPC 才成为独立 AI 联系人并进入正常聊天。

### 当前基线（已检查）

- `worldbook/characters/js/characters-manager.js` 中已有 `role.npcCharacters`，但它是某个主角色档案内的生活关系资料，并不是独立聊天联系人。
- 全局 AI 角色列表使用 `ai_custom_characters` / CharacterRepository。
- `shared/js/chat-notifier.js` 的现有主动联系逻辑只遍历已经存在的 AI 联系人，并要求用户逐个启用主动联系；它不会自动创建新联系人或发送好友申请。
- MAOMAO 已区分 `ai_role` 与 `real_user` 身份。NPC 必须是 AI 角色，不能伪装成真人账号。

### 实施阶段

**NPC-001A — NPC 生成与候选审核**
- 根据当前用户明确启用的主角色、已绑定世界书、关系网络和近期活动，判断是否有合理的新人物可以出现。
- 生成稳定 ID、姓名、头像引用、身份背景、性格、说话风格、相识理由、与已有角色的关系及生活近况。
- 生成后先成为待处理好友申请，不直接添加到已接受联系人。
- 采用频率限制、重复人物识别和关系一致性校验，避免无缘无故或大量生成。

**NPC-001B — 好友申请收件箱**
- 增加独立的 NPC 好友申请收件箱。
- 申请卡片展示 NPC 自我介绍和合理的认识缘由。
- 用户可以接受、拒绝、稍后处理或屏蔽。
- 同一 NPC 的重复事件必须幂等；拒绝/屏蔽后不得通过反复换 ID 绕过限制。
- 提供关闭自动发现、申请频率和安静时段设置。

**NPC-001C — 接受后成为聊天联系人**
- 用户接受后，创建或激活稳定的 AI 角色联系人。
- NPC 出现在现有通讯录和聊天列表，并能打开既有聊天详情页正常收发消息。
- 聊天历史、记忆、头像、设置和主动联系状态按 NPC ID 独立保存。
- 保留旧的 `role.npcCharacters` 人物关系档案，不批量迁移、不删除、不与新联系人数据混淆。

**NPC-001D — 后续主动活动**
- NPC 在用户启用的规则内自主判断是否发起联系；没有值得分享的内容时可以不发消息。
- 好友申请提醒和普通聊天消息提醒分开管理。
- 优先完成前台可见时的申请通知和状态闭环。
- 真实后台推送只有在服务端投递链路和真实手机设备验收通过后再接入；前台轮询不能标记为后台推送。

### 身份、隐私与权限边界

- NPC 始终使用 `ai_role` 身份，不进入真人账号 `real_user` 目录，也不调用真人好友 API。
- NPC 申请状态和关系生命周期必须有稳定 ID、明确状态和幂等保护。
- 不自动接受申请；用户拥有拒绝、屏蔽和关闭自动发现的控制权。
- 不跨主角色混用关系资料、聊天历史和记忆。
- 不自动读取无关角色聊天记录；只使用用户明确启用的上下文范围。
- NPC 不因此获得转账、红包、支付、钱包或真人交易能力。

### 验收

- 自动生成只产生待处理申请，不跳过用户同意。
- 接受、拒绝、稍后处理和屏蔽状态在刷新后保持。
- 接受后可以正常打开 NPC 聊天，收发消息。
- 每个 NPC 的聊天、记忆和设置隔离。
- 重复生成、拒绝后重发、申请频率和关闭开关均有自动化测试。
- 前台通知与真实后台推送分开验收，未完成设备测试前保持 NOT VERIFIED。

## 推荐交付顺序

1. **先做 LIB-001A / LIB-001B**：PDF 的普通文本提取和单词候选预览相对独立，可先交付一个真实可用的小闭环；OCR 与 AI 释义后续补齐。
2. **并行只读设计 MCP-001A**：先确认远程连接、授权和凭据代理方案，避免在安全后端尚未确定时把密钥存进浏览器。
3. **再做 NPC-001A / NPC-001B**：先实现独立申请收件箱与状态机，再把 NPC 接入现有 AI 联系人与聊天列表；不能把现有关系档案直接当成聊天联系人。
4. 每个阶段单独分支和 Draft PR，明确记录测试、真实手机验收、备份影响和未完成项。
