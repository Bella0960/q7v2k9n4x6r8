# MAOMAO｜唯一开发、测试与正式发布流程（执行总则）

> 2026-11-15 建立。**本文件是唯一发布流程入口**；`AGENTS.md`、其他工程手册、工作窗口和自动任务都应引用此文件，不得自行发明第二套发布顺序。
> 本文区分 **已核查事实** 与 **目标规则**。本次只是流程治理，不代表任何功能已经部署或手机验收通过。

## 0. 一句话规则

**需求 → 复用现有任务/PR → 任务分支开发 → 自动检查 → 独立 QA 实测 → 合并 main → 发布前安全门禁 → 获批准后发布 → 正式站复验 → 归档。**

任一阶段失败，退回原 PR 修复；**不新开一个功能相同的分支、不拿正式用户数据做测试、不因为合并就宣称上线。**

### 新窗口无需重贴长指令的默认开工机制（用户 2026-11-15 确认）

**本章适用于普通聊天、Work、自动任务及其他 AI 工程参与者。** 用户只需说“MAOMAO 开工”“继续小手机”或直接交代 MAOMAO 任务，执行者即须先读取仓库 `AGENTS.md` 的「MAOMAO 永久开工约定」、本流程、整改台账和原 PR；不得要求用户重复粘贴完整开工提示词。**项目治理以仓库文件为持久权威来源，账户聊天记忆不能代替实时 PR/构建/数据库证据。**

- **自检顺序不可省略：** GitHub 仓库和 main → 任务 ID/原 PR/依赖 → 文件所有权及是否已有其他窗口写入 → 影响的数据/样式/路由 → 在原分支开发或按指定角色只读 QA → 真实检查与唯一 QA → 整合及正式发布门禁。严禁自行开重复 PR、为赶进度跳步、用旧文件覆盖主线。
- **角色隔离：** 当 Work 被明确指定为独立验收窗口时，只读验证与反馈，不得与开发窗口并发修改同一文件；当被指定开发时才允许在明确认领的原分支操作。跨公共模块先交由单一负责人协调。
- **规则不可因缺额度失效：** CI 无步骤/测试未运行，标 `NOT VERIFIED / BLOCKED` 并保留 run ID、原因与解锁路径；不以静态检查冒充实机验收。可以在可用的非生产环境继续独立的安全任务。
- **最重要的保护边界：** 保留当前 HTML/CSS/JS + Cloudflare + PWA 与黑白灰既有 UI；管理员 `MAO-OXHBDBWCOIHPBBYN` 和正式用户数据不重置；单一状态栏/导航/存储职责；扩展接口渐进接入而非重写 90 页；唯一 QA、真机核验、生产备份恢复、明确发布授权缺一不可。
- **强制终点：** 每次报告必须明确 `原 PR / commit / 真实通过或阻塞的测试 / QA 设备与环境 / main 是否合并 / 生产是否发布及复验 / 下一步`；仅有 PR 或部署命令不代表用户可用。窗口结束时在原 PR/执行记录留可恢复交接，不得假称后台持续开发。

**注意：** 此为已经存在的唯一治理流程的开工入口，不创建新的流程、独立测试 Worker、数据库、外部工程或一套竞争规则。

## 1. 唯一工程、明确角色

- 唯一仓库：`Bella0960/MAOMAO`。唯一稳定代码基线：`main`。
- 一个功能一个主任务编号、一个主要负责人和一个**主 PR**；已有 PR 的，先继续原 PR。确实存在堆叠/依赖 PR 时，在主 PR 里写明前置 PR 和合并先后。
- 功能开发者只修改自己认领的文件；跨文件共享 API/数据库 schema 由一名负责人统一改。功能完成不等于发布。
- **发布协调者**只维护本流程、整合队列、QA 记录、发布记录。只有经过审核和授权的正式发布动作才能触碰生产配置。
- 禁止直接推送 `main`、强制覆盖历史、绕过验证自动合并、随意重置数据库、复建账号系统、为每次手机测试创建一个 Worker。
- 新功能必须沿用既有架构，预留可扩展接口/事件/注册点；不得以“整合”为由大面积回滚已验收的功能。

## 3. 单一任务状态（每个主 PR 只允许一个当前状态）

| 状态 | 判定标准 |
| --- | --- |
| `待开发` | 任务唯一、范围/负责人/验收标准已写明，搜索并引用了相关旧 PR |
| `开发中` | 在认领分支改动，未报测试通过 |
| `待修复` | 自动构建、单测、浏览器或 QA 实测有失败，返回**原 PR**处理 |
| `待 QA` | 代码检查通过、QA 可部署且环境隔离确认 |
| `QA 已通过` | 真实 QA 链路的功能验收通过，且记录了验证日期、版本、设备、账号类别 |
| `待发布` | 目标代码已审核/合并 main，安全门禁通过，尚未触发正式部署 |
| `已发布` | 正式入口对应版本和真实线上行为核对通过，可追溯部署 ID，已归档 |
| `阻塞` | 写明**具体阻塞原因、责任人与解锁条件**；不能用“差一点就好”替代 |

任务状态写在**主 PR 的顶部**，PR 模板为唯一记录格式。一个功能不可在多个 PR 各称“已经完成”；堆叠 PR 要注明上游和最终目标。

## 4. 固定实施顺序

1. **登记**：定义一句用户可感知的效果、任务编号、负责人、预计修改文件、不能动的原功能，搜索 open/merged PR。已有同功能主 PR 优先继续，禁止复制工作另起炉灶。
2. **开发**：从当前 `main`（或经明确标注的堆叠依赖）更新分支。兼容既有存储键、路由、角色 ID 和主题数据；变动跨模块契约先协调文件所有权。
3. **代码检查**：至少执行 `npm ci`、`npm run build` 与受影响模块真实存在的 Node 测试；需要时进行 Playwright/真实浏览器回归。无额度或未运行必须标 `未验证`，不能写绿色通过。
4. **唯一 QA 验收**：确认 QA Worker URL 与独立数据库和发布版本；用户在此试玩，支持 Android/Chrome 与 iPhone/Safari 的真实验收。不能用生产账号测试 QA，不能以 Node 模拟代替真机结果。
5. **代码整合**：由发布协调者检查与最新 main 的差异、上游依赖、冲突、测试证据、数据迁移方案和回滚路径；通过后合并至 `main`。多个功能需要联合测试时复用已有发布候选 PR，不并行造多份候选。
6. **正式发布前核验**：先做生产数据只读加密备份与隔离库恢复验收；核实管理员及已有普通账号连续性、Domain→Worker→Service Binding→DB 的实配、独立 Cloudflare Builds trigger 与 GitHub Actions；缺证据即阻止发布。
7. **明确批准后发布**：仅发布已审版本；记录 commit SHA、正式 Worker 版本、域名和操作人。功能分支、QA 分支绝不直接修改正式 Worker/DB。
8. **正式复验、回滚和归档**：验证 HTTP、登录、管理员、聊天保存、钱包记账、推送、缓存和 Android/iPhone 的关键场景。失败优先回滚 Worker 代码/触发器并保留原数据；**代码回滚不能自动恢复数据库**。主 PR 写入结论并归档。

## 6. 最终交付与跨窗口汇报格式

每次工作结束只汇报这七项，避免用户反复看不懂：

- **做的功能 / 唯一主 PR**
- **现在状态**（按第 3 节选择一个）
- **改了什么、保留了什么**
- **已实际跑过的测试 / 还没跑过的测试**
- **实际测试入口及所连数据库**（没确认就写未确认，不能编）
- **是否已合并 main / 是否已发布至 app.mao520.com**（分开写）
- **下一步唯一动作 / 明确阻塞**

用户不必手动操作 Git/端口来给每个 PR 验证 Node 测试；工作者优先自行执行，只有实际需要 Android/iPhone 现场验收时才给出**一个可验证的测试入口**和简短操作。
