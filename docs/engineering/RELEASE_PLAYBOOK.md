# MAOMAO｜唯一开发、测试与正式发布流程（执行总则）

> 2026-11-15 建立。**本文件是所有任务共有的开发质量与发布门禁规则，而不是要求每个开发窗口都执行发布工作。** `AGENTS.md`、其他工程手册、工作窗口和自动任务应引用此文件，不得自行发明第二套发布顺序。
> 本文区分 **已核查事实** 与 **目标规则**。本次只是流程治理，不代表任何功能已经部署或手机验收通过。

## 0. 一句话规则

**对每项任务分别遵守：需求 → 复用原任务/PR → 实际开发 → 对应自动测试 → 达到验收条件后唯一 QA → 审核/授权合并 main；只有进入正式发布阶段时，才继续执行生产安全门禁 → 用户明确批准 → 正式站部署 → 线上复验/归档。**

任一阶段失败，退回原 PR 修复；**不新开一个功能相同的分支、不拿正式用户数据做测试、不因为合并就宣称上线。**

### 新窗口无需重贴长指令的默认开工机制（用户 2026-11-15 确认）

**本章适用于普通聊天、Work、自动任务及其他 AI 工程参与者。** 用户只需说“MAOMAO 开工”“继续小手机”或直接交代 MAOMAO 任务，执行者必须先读取 `AGENTS.md` 的「MAOMAO 永久开工约定」、本流程、整改台账和原 PR；**但默认开工指令只让执行者按规则继续所认领的实际任务，绝不表示默认转向状态栏 PR #301、测试版本或正式发布。** 不得要求用户重复粘贴完整开工提示词。项目治理以仓库文件为持久权威来源，账户聊天记忆不能代替实时 PR/构建/数据库证据。

- **按实际阶段汇报，不许长篇原地打转：** 开发窗口优先汇报**真实代码、修复了什么、原 PR/commit、实际测试及下一项开发动作**；未到 QA/整合/发布阶段只需简记“未进入”，**禁止反复强调测试版/正式版或空谈门禁来代替推进代码**。只有负责 QA/整合/发布的窗口才需详细填写对应环境、设备、数据库及生产复验；结束时在原 PR/执行记录留可恢复交接，不得假称后台持续开发。

### 跨窗口测试去重与集中发布纪律（2026-11-18）

**先做差异影响判断，再选择验证范围。** 原 PR 日常修改仅执行相关 Node/浏览器测试或必要的局部构建；已通过且源码、依赖、环境未受影响的检查复用现有 SHA/日志证据，禁止每次修一个样式就重新执行全仓测试、全量构建和部署。多窗口各自完成原 PR 的定向验证及交接，由唯一 QA 整合窗口集中吸收变更，并在完整候选形成、实际依赖变更或需要进行发布门禁时才统一执行必要的构建/全套回归和部署。失败仅重测受影响项，除非修复触及其依赖链或整个候选版本变化需要重验。不得牺牲账号隔离、数据安全、真机及用户验收等发布要求。可由连接的 GitHub 工具完成的工作优先直接完成，避免无必要地让用户操作 Codespaces/终端；没有真实执行权限时，只给出单次最小必要操作，不把重复劳动转嫁给用户。

## 0A. 全局治理任务与专项任务严格分离（强制防误分流）

1. **“统一项目流程”是全体执行者应遵守的工作纪律，不是一个必须占用所有窗口的开发专项。** 工作窗口首先执行用户当前委派的实际代码任务；不得自行把它缩小成状态栏/QA/正式发布。
2. **“统一 MAOMAO 架构”是独立的跨模块工程目标**：沿用现有原生 HTML/CSS/JS、Vite/Cloudflare/PWA，渐进统一手机壳、App 注册与导航、页面生命周期、全局设置/状态栏、样式隔离、模块扩展点、角色与存储接口。已有不同专项的 PR 与文件所有权必须尊重，公共层只由协调分配的负责人修改，不能推倒重写或仅写方案。
3. **状态栏 `UI-STATUS-001` / PR #301 只是已认领的一个子模块**，除非本窗口已被用户或协调者明确委派，否则不能自动接手 #301、以其测试失败为理由暂停整体架构/聊天/钱包/论坛等无冲突开发；必须优先检查任务台账，找当前授权且未被认领的实际工作。
4. **统一开发标准不等于所有模块锁步发布。** 每个 PR 各自开发、跑相关测试、满足条件后在唯一隔离 QA 验收。某 PR 因 CI/QA/授权受阻，不会改变另一独立 PR 的开发权限；只有同一共享文件、功能依赖或安全门禁确实相关，才允许写明证据阻塞对应工作。
5. **只在接近发布时讨论生产门禁。** 用户明确未批准正式版本：不得合并或部署未经授权的内容；但开发窗口不得反复输出“不能发布正式版”来替代具体工程产出。
6. **每轮优先提供有证据的实际产出**：本轮实际修改文件、修复/新增的真实功能、commit/原 PR、已经跑过的相关测试、下一个开发动作。只有进入 QA、合并与发布阶段时才扩展环境和验收报告。

**纠错规则：** 如果一个窗口把“MAOMAO 开工，按统一工程规则继续”解读成“所有窗口都去修 PR #301、准备测试版和正式版”，属于**任务分流错误**。必须立即停止该误分流，重新核实用户当前授权、原 PR 与文件所有权，并返回实际开发；不得要求用户再次复制长指令纠错。

## 0B. GitHub Actions 已知不可用时的替代测试制度（强制，不得再拖进度）

**用户已经反复明确：MAOMAO 仓库 GitHub Actions 的可用额度/runner 已无法承担当前测试。** 历史记录里曾有 PR 检查短时返回 `failure`，但 job 没有任何 steps。此时**测试根本没有执行**，不能断言代码失败，更不能默认“每天再试一次 GitHub CI”。**将 GitHub Actions 作为日常开发的依赖、频繁汇报它又失败，属于流程执行错误。**

### 1. 单一既知外部阻塞，不再每天重复调查

- GitHub Actions 默认标记 `CI_UNAVAILABLE — known external runner/quota limitation`。若未获得额度恢复的新证据或用户明确要求，不得持续轮询、重试 workflow、增加无关提交触发检查、建立新 CI 工作流或重复把此问题列为本日主阻塞。
- **停止的只是“依赖 GitHub Actions 执行测试”**，不是停止开发、更不是取消质量检查。所有窗口仍应在其原 PR 继续实现与修复。
- 不把无法启动的 GitHub workflow `failure` 计为代码单测失败；遇到真实可运行测试失败，才标 `CODE_TEST_FAILED` 并回原 PR 修复。

### 2. 固定采用可执行的离线/隔离替代路线

优先在已有可用的本地电脑、Work 独立工作环境、可信隔离执行容器中检出对应 PR 的**准确 commit SHA**；不使用正式账号、正式数据库或生产 Worker 做实验。

1. 环境准备：核对 Node/npm 版本和项目锁文件；可运行时执行 `npm ci`。
2. 实际运行本次改动涉及的既有 Node 测试，例如 `node --test tests/<实际文件>.test.mjs`；**必须确认文件真实存在，禁止虚构命令或声称只读源码就“通过测试”**。
3. 执行 `npm run build`；检查资源及服务入口不退化。必要时在真实浏览器/Playwright 中按本次改动复现，关注导航、刷新、状态栏、角色数据隔离与 PWA。
4. 每次验收将证据附回**原 PR**：日期、测试 commit、执行机器/容器及 Node/npm 版本、完整命令、退出码、关键输出、失败复现与修复后再次运行结果。需要时提供截图/视频/日志，但不得包含密钥、生产账户和私人数据。
5. 若当前窗口根本没有可执行代码的环境，必须明确标 `NOT RUN — NO EXECUTION ENVIRONMENT`，不要继续假装查 GitHub workflow；将需要运行的确切命令与代码版本交给**已存在的、具备执行能力**的窗口/环境，并继续其他无冲突、已授权的代码开发。不得因一项无法验证而把全项目置于只读报告状态。

### 3. 不降低真正门禁，也不得让外部 CI 扣住全项目

- **本地/隔离真实执行后的通过证据，可以作为工程审查与进入唯一 QA 的验证材料**；GitHub Actions 不可用不等于这些证据无效。
- **如果 GitHub 当前分支保护/规则集技术上要求特定 Actions check，不能自行修改保护规则或通过绕过/强推冒充通过。** 这种情况下仅该 PR 的合并仍受技术门禁约束；记录阻塞并由有权限的责任人评估符合仓库规则的替代验证方案和必要授权，其他独立任务继续开发。
- QA、Android/iPhone 真机、正式备份恢复、管理员连续性及用户明确发布授权仍是各自阶段的真实要求，不能用 `CI_UNAVAILABLE` 作为跳过这些门禁的理由。
- GitHub CI 日后恢复时再纳入额外验证，但不得把恢复 GitHub Actions 当作 MAOMAO 功能开发的前置条件或每天主动追踪的默认任务。

### 4. 对用户的汇报纪律

**正常开发日报只汇报实际代码与进度**：这次修了什么、原 PR/commit、哪些本地测试真实跑了、哪个真实问题仍阻塞下一步。GitHub Actions 的既知额度/runner 问题**无新变化就不再提**。若真正涉及 PR 合并且规则技术上阻止操作，用一句话说明，不许写成长篇重复解释，更不得要求用户为了同一错误反复协助。

## 0C. 唯一长期完整测试小手机与用户亲自验收制度（2026-11-16 强制新增）

**用户最终要求：MAOMAO 一部长期可使用、持续保留数据的完整隔离测试小手机，所有新功能先接入它，用户亲自放入 API、真实使用并反复修复验收；只有在这份完整体验验收通过后，才能按另一次明确授权升级正式版。** 这是一项**所有功能到达 QA 阶段时的统一产品验收标准**，不是让每个开发窗口每天停工讨论“测试版/正式版”。

### A. 唯一测试环境必须是完整的小手机，不是独立样板

1. **唯一长期 QA，不新建每功能一个环境。** 先核查现有 QA Worker `maomao-aw-qa-20261114` 的可用访问 URL、版本、完整前端、账号身份绑定和独立数据库；验证后才可公布给用户。不得直接使用生产账号、生产 DB 或凭 `preview.mao520.com` 名字认作 QA，不得虚构测试链接。
2. **新功能原 PR 修好并完成可运行的代码验证后，应集成到这个已核实的完整 QA 应用中**，以已有聊天、角色、世界书、论坛、主题、设置、钱包等真实模块和调用方式验证。独立 HTML、单页设计预览、Mock/假接口、静态图片与分支截图，只允许做局部设计评审，**绝不属于完整功能验收或发布批准**。
3. **原地升级，测试数据持久。** 版本迭代不允许默认清除/覆盖用户在 QA 中建立的角色、聊天、图片、设置、世界书、长期记忆和必要 API 配置。必须核对既有存储实现、账号作用域、schema 兼容、加密备份覆盖、恢复演练与失败回退；未验证的备份不可声称可恢复。清除 QA 数据、密钥或做破坏性重置必须另获用户明确授权，不能以“只是测试版”为由随意处理。
4. **功能联动优先。** 要能在完整页面来回切换、刷新/重启、跨日使用，并检查登录、角色隔离、聊天历史、AI 回复、图片/语音、群聊、论坛、PWA 更新、推送/深链接以及钱包模拟流程。不同功能只验收受本次改动实际影响的路径；不要求每个小改动都重新全站测试，但整批发布前需做受影响关键场景的集成回归。

### B. 用户可以在 QA 安全接入真正 API 后验收

1. 提供**现有且经过安全核验的设置途径**供用户自己输入、测试和更换 API 配置；在具备真实调用条件时，实际测试 AI 对话、图像、语音、角色连续记忆及服务端错误处理。未经真实接口验证，仅可标 `MOCK_ONLY / API_NOT_VERIFIED`，不能称为完整 AI 功能已通过。
2. 禁止把用户 API Key 放进聊天、GitHub、公开 HTML/JS、构建文件、PR 日志、浏览器 URL 或截图；优先沿用既有安全配置机制，并审查权限隔离、密钥存储位置/导出和撤销方式。**若现有客户端密钥方案不足以满足保密要求，先停止相应真实密钥测试并完成安全修复，不得为方便测试创建明文共享密钥库。**
3. 真正 API 可能计费，也可能把测试内容发送给提供商；应在测试设置中清晰提示，支持用户自行限制用量、撤销/更换 Key。QA 中使用**独立测试身份和测试数据**，绝不复制正式聊天记录、账号/支付信息或凭据来填充测试版。

### C. 只有用户使用完整 QA 后才存在验收结论

- **开发者验收**：代码、Node/build、浏览器、存储检查是真实可验证的工程证据，只能决定「是否可进入完整 QA」，不能替用户判断满意度。
- **用户完整体验验收**：用户在唯一 QA 使用自己的测试角色和 API，实际走通本次变更核心情景（必要时 Android Chrome / iPhone Safari）、跨页数据写入与重启/刷新恢复，明确回报“此版此功能验收通过”并记录 **QA 入口、部署 SHA/版本、日期、测试账号类型、功能范围、API 是否真实连通、已知问题**。不要求公开 Key、账号凭据或聊天内容。
- **发现问题必须原地修复**：在负责该功能的原 PR 修复，重新执行相关测试，把修复版本部署回**同一部 QA 小手机**，保留旧测试数据，由用户再次实测。不能用另造一个空白独立预览代替。
- **一批经过用户体验验收的代码才能成为正式版候选**。用户只说“界面好看”“预览可以”或“代码完成”，**都不是这批候选的完整验收同意，更不是正式发布许可**。正式部署需要**另外针对具体发布版本的明确批准**，继续遵守最新 main 差异、加密可恢复备份与隔离恢复、账号连续性、Worker/DB/触发器、回滚等原有门禁。
- **正式与 QA 是两个独立数据空间**：正式部署只更新已审核的程序版本和经单独授权且可回退的数据迁移；**不得把 QA 中的用户角色、测试消息、API Key、测试身份/会话、钱包模拟交易直接复制或覆盖到正式库**。发布成功后应验证正式站账号、数据连续性和关键流程，必要时按既定方案回滚代码并保护现有数据。

### D. 清晰区分四种真实状态

- `DESIGN_PREVIEW_ONLY`：仅外观/动画或独立页预览，**不能算完整功能 QA**。
- `QA_READY_NOT_USER_ACCEPTED`：已连接完整隔离 QA，开发者验证已完成，但用户尚未实际验收。
- `QA_USER_ACCEPTED`：用户在固定完整测试小手机实际使用并明确验收了指定 QA 版本及功能范围，**不等于批准发布**。
- `PRODUCTION_RELEASE_APPROVED`：用户在核对具体候选及正式安全门禁后另行明确批准；部署成功/线上复验仍需独立记录。

**高优先级产品门禁：** 任何窗口不得把“独立页面做出来”“测试 API 是假的但布局好看”“已部署某个临时 URL”标记成 `QA_USER_ACCEPTED`。也不得用未经核验的现有 QA Worker 名称冒充已构建完整可玩的测试环境。所有每日开发任务继续正常推进，待功能具备条件时才履行本节验收标准。

## 1. 唯一工程、明确角色

- 唯一仓库：`Bella0960/MAOMAO`。唯一稳定代码基线：`main`。
- 一个功能一个主任务编号、一个主要负责人和一个**主 PR**；已有 PR 的，先继续原 PR。确实存在堆叠/依赖 PR 时，在主 PR 里写明前置 PR 和合并先后。
- 功能开发者只修改自己认领的文件；跨文件共享 API/数据库 schema 由一名负责人统一改。功能完成不等于发布。
- **发布协调者**只维护本流程、整合队列、QA 记录、发布记录。只有经过审核和授权的正式发布动作才能触碰生产配置。
- 禁止直接推送 `main`、强制覆盖历史、绕过验证自动合并、随意重置数据库、复建账号系统、为每次手机测试创建一个 Worker。
- 新功能必须沿用既有架构，预留可扩展接口/事件/注册点；不得以“整合”为由大面积回滚已验收的功能。

### 两个唯一正式网址与现有别名的实际边界（2026-11-16 只读复核）

**用户对外只认 `mao520.com` 与 `app.mao520.com` 两个正式入口。** Cloudflare Custom Domain 当前分别指向 `mao-auth-preview` 和 `curly-dream-324c`。额外启用的 `auth`、`login`、`admin`、`static`、`ivory` 子域名为历史或兼容入口，`preview` 当前已停用；它们不能被继续包装成多个用户需要记住的新正式站。**是否可以关闭、改跳转或者删除旧 Worker 必须先审查真实登录、推送、静态资源及认证回调依赖；不得凭名字“preview”误删正式身份服务。**

`curly-dream-324c` 虽有 `MAO_APP_BACKEND`→`maomao-aw-qa-20261114` Service Binding，但 `MAO_APP_CUTOVER_ENABLED=false`，不能将“存在绑定”说成“已完成新版切换”。现有 QA Worker 虽有独立 `CLOUD_DB`，却将 `MAO_IDENTITY_AUTHORITY` 指向 `maomao-001-identity-gateway-20261114`（production），当前只核实了配置，**没有证明测试登录不会影响正式身份系统**。

本次新增专项 `DOMAIN-ENTRY-001`（详见 `REMEDIATION_BACKLOG.md`）要求：先梳理并实测旧别名/路由/凭据/数据隔离，安全准备一个稳定、完整、真正可玩且与正式站不同 origin 的既有 QA 入口供用户验收，**不添加第三个对外宣传的正式域名、不在 `app.mao520.com/qa` 未经隔离评估地混用本地存储、Cookie 或 Service Worker**。如两个可见正式域名与完全独立 QA 的实施细节有冲突，应在原整合 PR 给出已验证的最小实现，不能擅自改生产路由或生产身份。**该专项不允许借域名治理名义阻塞其他无文件冲突的日常开发**。

### 配置与实际发布要分开

- 仓库 `wrangler.jsonc` 当前指向 Worker `mao`，并**不是** `app.mao520.com` 所绑定的 `curly-dream-324c`。
- `.github/workflows/deploy-cloudflare-worker.yml` 当前只有 `workflow_dispatch`，**不是 push main 就自动完成正式小手机发布**。其部署目标是 `mao`；工作流成功不代表 `app.mao520.com` 已更新。
- 其他 Cloudflare Builds/触发器和域名 Worker 版本必须作为**单独发布门禁**读取并核验。不得仅凭 GitHub Actions 绿灯判断实际正式域名已更新；发布前检查是否存在旧静态自动构建覆写现网的触发器。
- **现阶段仅冻结未经批准的正式版发布，不冻结开发、功能修复、架构整改或隔离测试工作。** 发布前必须完成正式账号/数据可恢复备份及隔离恢复、同源链路验证、Android/iPhone 验收、真实触发器核对和明确发布授权。各无冲突模块的实际开发可以继续并行推进；禁止把这条生产门禁解释为“开发人员只能继续讨论发布或测试”。

## 3. 单一任务状态（每个主 PR 只允许一个当前状态）

| 状态 | 判定标准 |
| --- | --- |
| `待开发` | 任务唯一、范围/负责人/验收标准已写明，搜索并引用了相关旧 PR |
| `开发中` | 在认领分支改动，未报测试通过 |
| `待修复` | 自动构建、单测、浏览器或 QA 实测有失败，返回**原 PR**处理 |
| `待 QA` | 代码检查通过、QA 可部署且环境隔离确认 |
| `QA 已通过` | **必须是用户在唯一长期完整 QA 小手机中亲自试玩指定版本/功能、按需接通真实 API 并明确确认**；记录 QA URL/版本 SHA/日期/设备/测试账号类型/验收范围，不能只凭单页预览、Mock、开发者 Node/浏览器检查；QA 通过不等于正式发布批准 |
| `待发布` | 目标代码已审核/合并 main，安全门禁通过，尚未触发正式部署 |
| `已发布` | 正式入口对应版本和真实线上行为核对通过，可追溯部署 ID，已归档 |
| `阻塞` | 写明**具体阻塞原因、责任人与解锁条件**；不能用“差一点就好”替代 |

任务状态写在**主 PR 的顶部**，PR 模板为唯一记录格式。一个功能不可在多个 PR 各称“已经完成”；堆叠 PR 要注明上游和最终目标。

## 4. 固定实施顺序

1. **登记**：定义一句用户可感知的效果、任务编号、负责人、预计修改文件、不能动的原功能，搜索 open/merged PR。已有同功能主 PR 优先继续，禁止复制工作另起炉灶。
2. **开发**：从当前 `main`（或经明确标注的堆叠依赖）更新分支。兼容既有存储键、路由、角色 ID 和主题数据；变动跨模块契约先协调文件所有权。
3. **代码检查**：**默认不依赖不可用的 GitHub Actions**，优先在可用的本地/Work/隔离环境实际执行 `npm ci`、`npm run build` 与受影响模块真实存在的 Node 测试；需要时进行 Playwright/真实浏览器回归，附 commit/命令/退出码证据。Actions 没额度属已知外部限制，**不反复重试/汇报，不停止其他开发**；未运行只标 `NOT RUN`，不能写通过。完整替代制度见第 0B 节。
4. **长期完整 QA 真实使用与用户验收**：在同一部已核实可访问、身份及数据库与正式站隔离的完整测试小手机**原地迭代功能、保持 QA 数据不被更新清空**。用户通过受保护设置接入真实 API，亲自体验角色、聊天、记忆及功能联动，Android Chrome/iPhone Safari 按受影响范围实测；独立设计页/Mock/Node 自动测试不算用户功能验收。用户明确确认指定 QA 版本后才标「QA 已通过」，具体见第 0C 节。
5. **代码整合**：**经用户完整 QA 体验验收的版本**由整合负责人检查与最新 main 的差异、上游依赖、冲突、真实测试与用户验收证据、数据迁移方案和回滚路径；按照既有授权及分支保护规则审核/合并至 `main`。未获用户完整 QA 验收的功能不得被擅自塞进正式候选。多个功能联合测试复用唯一 QA/现有发布候选，不另建许多临时环境。
6. **正式发布前核验**：先做生产数据只读加密备份与隔离库恢复验收；核实管理员及已有普通账号连续性、Domain→Worker→Service Binding→DB 的实配、独立 Cloudflare Builds trigger 与 GitHub Actions；缺证据即阻止发布。
7. **明确批准后发布**：仅发布已审版本；记录 commit SHA、正式 Worker 版本、域名和操作人。功能分支、QA 分支绝不直接修改正式 Worker/DB。
   **提示：** 本流程中的「用户在完整测试版验收通过」和「用户明确批准正式发布」是**两次不同的授权**；前者认可具体功能体验，后者才允许指定正式版本在所有门禁满足后部署。
8. **正式复验、回滚和归档**：验证 HTTP、登录、管理员、聊天保存、钱包记账、推送、缓存和 Android/iPhone 的关键场景。失败优先回滚 Worker 代码/触发器并保留原数据；**代码回滚不能自动恢复数据库**。主 PR 写入结论并归档。

## 6. 最终交付与跨窗口汇报格式

每次工作结束只汇报这七项，避免用户反复看不懂：

- **做的功能 / 唯一主 PR**
- **现在状态**（按第 3 节选择一个）
- **改了什么、保留了什么**
- **已实际跑过的测试 / 还没跑过的测试**
- **实际测试入口及所连数据库**（没确认就写未确认，不能编）
- **是否已合并 main / 是否已发布至 app.mao520.com**（分开写）
- **下一步唯一动作 / 明确阻塞**

用户不必手动操作 Git/端口来给每个 PR 验证 Node 测试；工作者优先自行执行，只有实际需要 Android/iPhone 现场验收时才给出**一个可验证的测试入口**和简短操作。
