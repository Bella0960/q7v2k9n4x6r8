# MAOMAO 真人好友文字聊天 MVP

## 当前范围

本阶段在现有「新的朋友」好友关系之上，增加两个已互相同意好友之间的纯文字聊天：

- 好友列表中的「聊天」入口打开独立聊天页面。
- 消息保存在 Cloudflare Worker 绑定的 Durable Object SQLite 中，方便双方跨设备读取。
- 聊天页可载入最近 50 条记录，并按游标向上读取更早消息。
- 聊天页在前台可见时每 4.5 秒轮询新消息；切到后台后暂停轮询。
- 好友列表显示云端未读条数，并每 12 秒在前台刷新一次。
- 每位好友分别保存当前用户的已读游标；只有对方消息气泡进入聊天可视区域后才确认已读，跨设备共享未读状态。
- 可以单条隐藏消息，也可以清空当前账号这边的整段会话；隐藏/清空均不会删除好友账号里的原消息，清空水位线之后的新消息仍会正常出现。
- 客户端消息 ID 提供幂等保护，发送请求超时后使用相同 ID 重试不会重复插入。
- 每条消息最多 2000 个 Unicode 字符，只接受非空文字。
- 每个真人账号最多每分钟新建 60 条消息；同一条已保存消息的网络重试不重复计入额度。

## 权限边界

- 每个读写接口都重新验证真人账号凭据。
- 同一对账号无论谁先发起，都最多只有一条待处理好友申请；互相同时发起时，以先进入数据库的申请为准，另一方收到“对方已申请”的提示。
- 好友申请的同一处理结果可以安全重试；例如同意请求的响应丢失后再次同意仍返回成功，但“同意”与“拒绝”冲突时，以先完成的结果为准，不会被后续请求覆盖。
- 只有好友关系表中仍然存在的双向好友关系才能读取或发送。
- 删除好友后，双方立即无法再通过消息 API 读取、发送、更新已读状态或执行消息隐藏/清空。
- 已读游标只能由收件人针对确实发给自己的消息推进，且只允许向前移动；较旧设备迟到的确认不会把游标倒退。
- 客户端不能通过请求体写入图片 URL、附件或任意额外字段。
- 消息正文在页面中通过 `textContent` 渲染，不作为 HTML 执行。
- 服务端消息 ID 和游标由服务端生成；游标使用会话内严格递增的创建时间与消息 ID。

## 数据与隐私说明

- **当前聊天正文以普通文字形式保存在 MAOMAO 云端 SQLite 中，不是端到端加密。** 任何用户在试用前都应知晓这一点；不要把密码、验证码、支付信息或其他敏感内容发到当前 MVP。
- 消息不会发送给 AI 角色，也不会交给 AI 模型处理。
- 当前只存储文本、双方真人账号 ID、消息 ID 与创建时间；不存储图片、语音、位置或附件。
- 单条隐藏与清空会话只改变当前账号的可见性，不会删除云端原消息，也不会影响好友的视图；当前没有真正从云端永久删除消息的功能。删除好友会结束当前聊天代际：旧消息行保留在云端，但重新添加后会创建新的 `generation_id`，新会话查询、未读统计、清空、隐藏和已读确认都只作用于新代际，因此旧历史不会重新出现。删除时会清理双方各自的已读游标、清空水位线和隐藏覆盖状态；迁移 `0010` 也会清理此前已删除关系遗留的孤立视图状态，同时保留仍有效好友关系的视图状态。旧关系中的消息重试会被拒绝，必须作为新消息重新发送。旧的已接受申请重复提交同意只返回幂等成功，不会重建已删除的好友关系。
- 当前没有后台推送，也没有向发送方显示的送达/已读回执。只有打开聊天页且页面处于前台时，才会轮询新消息。

## 接口

- `GET /api/friends/:friendId/messages`：读取最近一页消息。
- `GET /api/friends/:friendId/messages?after=<createdAt>.<messageId>`：读取游标之后的新消息。
- `GET /api/friends/:friendId/messages?before=<createdAt>.<messageId>`：载入更早消息。
- `POST /api/friends/:friendId/messages`：发送纯文字，请求体仅允许 `clientMessageId` 与 `body`。
- `DELETE /api/friends/:friendId/messages/:messageId`：只在当前账号隐藏单条消息。
- `DELETE /api/friends/:friendId/messages`：只清空当前账号这边的整段会话。
- 消息分页同时返回当前账号的 `viewState.version`，其中包含当前好友关系代际；其他设备发现隐藏、清空或关系代际变化后会重新加载当前会话视图，并重置旧消息游标。

所有接口都需要 `X-Maomao-Account` 认证，并再次验证双方好友关系。

2. 再合入并验收 PR #196 的真人账号、二维码与好友关系。
3. 最后合入本 PR；首次 Worker 部署会按迁移顺序创建 `0006_friend_messages`、`0007_friend_conversation_reads`、`0008_friend_message_visibility`、`0009_friend_request_pair_uniqueness` 与 `0010_friendship_generation_isolation`。0009 会先收敛历史反向重复待处理申请，再建立按无方向好友对唯一的数据库索引；0010 会为现存好友关系和消息回填代际，并清理已不存在好友关系的孤立视图状态。
4. 用两台真实设备分别创建真人账号，互扫二维码、发送并同意好友申请。
5. 双向发送文字，验证轮询、刷新恢复、向上翻历史、断网重试无重复；删除好友后确认访问被拒绝，再重新添加同一好友，确认旧消息、未读、隐藏和清空状态均不恢复，旧消息 ID 与旧 clientMessageId 不能跨关系重放。
6. 真实部署与 Android PWA 验收仍需独立完成；本地契约测试或静态构建不能替代真机验收。
