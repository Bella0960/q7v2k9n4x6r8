# FTR-001 — 角色互动随机玩法：抽签 / 大转盘 / 塔罗 / 今日运势

**状态：IN PROGRESS · 第一轮功能实现已提交 PR，待真实设备验收**  
**目标仓库：** `Bella0960/MAOMAO`  
**基线分支：** `main`  
**任务分支：** `FTR-001/role-play-luck-room`

## 1. 用户目标

在 MAOMAO 中新增一个独立应用，统一容纳四种轻量互动玩法：

1. 抽签
2. 大转盘
3. 塔罗牌
4. 今日运势（“今天我运气如何”）

四个玩法都支持选择任意一个已有角色共同参与，也支持独自体验。角色必须真正参与开始前和揭晓后的互动，而不是只在页面上显示头像。选择角色后，角色能结合自身人设、称呼、语气和必要上下文自然回应；用户随时能切换角色。

## 3. 总体视觉要求（硬性要求）

用户强调本应用必须“好看、精致”，沿用 MAOMAO 的视觉系统：

- 黑、白、灰为主；编辑式极简、独立设计刊物感。
- 用留白、字体层次、细线、精确对齐、精致排版和有意义的微动效建立质感。
- 不要把四个入口做成四张普通大卡片，不要堆成普通功能列表，也不要做卡片墙。
- 禁止紫色星空、蓝粉渐变、霓虹、发光边缘、玻璃彩光、厚重阴影、Emoji/颜文字、无意义英文装饰。
- 以 375–430px 手机视口优先，同时适配桌面壳。首屏要有明确视觉重点，不能空旷、杂乱或塞满说明文字。
- 四个玩法各自拥有贴合操作的独特视觉和动效，但整体看起来属于同一个 MAOMAO 应用。
- 动效轻、顺、短，服务于操作；禁止无意义持续循环和大幅弹跳。
- 不得为了“统一”而覆盖项目已有主题选择或用户自定义数据。

### 3.1 塔罗牌外形——用户特别强调的硬性要求

**塔罗牌绝对不能长得像普通扑克牌，也不能使用普通圆角矩形卡片。**

用户指定的造型是：竖长比例、类似切割水晶/晶体的六角形牌体。轮廓具有清楚的六个角/六个折面，顶部收成尖角，底部通过斜切折面收束成角，左右边缘形成有方向的晶体切面。整体要像一枚竖立的、经过切割的长形水晶，而不是常规纸牌外框。

造型落实要求：
- 竖长的水晶六边形轮廓，六角/六面特征可辨认；上端尖，下端斜切并形成折角。
- 使用细线、内外双层轮廓、少量切面分割、对称或有秩序的几何图案来表现晶体质感。
- 牌背、牌面、翻牌过程都要保持这种水晶牌体轮廓；翻面不能突然变回普通矩形。
- 牌组散开、洗牌、选牌、翻面和牌阵排布时，必须保持竖长比例、切面轮廓和手机触控下的可读性。
- 黑白灰为主，可用明暗、线条密度、透明度、纸面/矿物质感建立层次；禁止紫色星空、蓝粉渐变、霓虹光晕等常见俗套占卜视觉。
- 牌面符号、牌名、数字和牌意层级清楚，不要把文字压在复杂纹样上。
- 需提供真实手机尺寸下的牌背、单张翻面、三张牌阵视觉截图，证明不是普通扑克牌改色。

## 4. 四种玩法功能范围

### 4.1 抽签

- 支持创建多个签筒/签池，例如「午餐吃什么」「周末做什么」「今日小任务」。
- 每个签池可新增、编辑、删除签条；默认模板可修改；自定义签池保存后刷新仍存在。
- 真实可操作的摇签、抽出、展开结果动效；结果清楚展示。
- 支持用户抽、角色抽、轮流抽等简单自然的参与方式。
- 结果由独立随机逻辑产生，不由 AI 选择。

### 4.2 大转盘

- 可编辑转盘标题和选项：新增、修改、删除；选项数量动态变化时，扇区和标签要正确布局。
- 支持保存多套转盘模板，提供可编辑示例，如「中午吃什么」「周末做什么」「看什么」「谁来决定」。
- 点击开始后有流畅旋转、减速、停止动效；指针停留的扇区必须与实际随机结果一致。
- 使用明确的随机逻辑决定结果；AI 不得改结果、影响权重或重抽直到满意。
- 转盘结果可由角色参与回应。

### 4.3 塔罗牌

- 至少支持单张牌与三张牌阵（过去 / 现在 / 未来）。
- 洗牌、选择、翻牌、牌阵呈现要有完整连贯的交互流程。
- 塔罗牌实现完整 78 张牌：22 张大阿卡纳，以及权杖、圣杯、宝剑、星币四组各 14 张小阿卡纳。每张牌具有独立关键词、正位/逆位解释与牌面符号。
- 支持正位/逆位的娱乐性解释，语气温和、开放，不写成必然发生的预言。
- 牌名、牌面符号、正逆位解释、关键词需采用结构化数据，不要只随机生成一段文案。
- 牌面艺术采用原创、克制的黑白线刻/几何纹样，不搬用未经授权的商业塔罗牌套图。
- 牌的外轮廓必须遵守第 3.1 节的竖长水晶六角造型。禁止常规矩形纸牌、圆角长方形或扑克牌外观。

### 4.4 今日运势

- 设置独立的「今天我运气如何」玩法入口。
- 结果可包含综合趣味指数、今日关键词、轻量分类提示（如学习/创作/社交/休息）和一句今日小建议。
- 结果为随机娱乐内容，不包装成科学结论或真实预测。
- 可提供「再测一次」，明确这是重新进行一次随机娱乐体验。
- 选中的角色可以一同参与并作出符合人设的自然反应。

## 5. 角色联动与数据隔离

- 四个玩法均可选择「独自体验」或从项目真实角色列表中选择任意角色；不可写死角色名单或虚构角色 ID。
- 角色回应复用项目现有 PhoneAPI / PhoneContext 等能力，不另造一套 API 客户端、角色系统或上下文装配逻辑。
- 角色只负责互动与解读，不得决定、修改或操纵抽签、转盘、塔罗、今日运势的随机结果。
- 游戏模板、游戏历史和角色关联记录有清晰数据边界；不同角色记录不可串号。用户自定义内容刷新后仍应保留。
- 不要将每次小游戏互动伪装成真实聊天消息写入 `chat_history_<roleId>`。除非未来用户主动使用明确的分享入口，否则记录应留在本应用自己的数据域。
- 优先复用已批准的存储封装；不要创建共享存储架构、改聊天数据结构或批量迁移数据。
- 写入失败必须明确提示，不能假报保存成功。API 失败时，随机玩法本身仍可独立运行。

## 6. 强制免责声明——逐字一致

以下文字必须显示在**四种玩法每一个结果页的底部**，不能只放在应用首页、弹窗、设置页或开始前提示中。塔罗牌尤其必须清晰可见：

> 以上内容均为娱乐体验，不具备预测未来或指导现实决策的作用，请勿当真，一切仅供娱乐参考。

建议塔罗开始前也低干扰提示一次，但开始前提示不能代替结果页底部固定免责声明。

角色生成的解读也必须遵守这一边界：不把牌意或运势说成必然事实，不对健康、财务、法律或重大人生决策给出预测或指令。

## 7. 启动器与集成

- 新应用必须从 MAOMAO 当前正式桌面/启动器正常进入，并兼容当前图标管理、排序、拖动、隐藏等既有机制。
- 不为新增入口重做桌面，不覆盖用户当前桌面布局或图标自定义数据。
- 保持原生 HTML/CSS/JS 多页面架构；不引入 React/Vue 或新框架。
- 路由、返回行为、状态栏/刘海安全区、底部 Home Indicator 和移动端触控正常。
- 只在必要范围内新增页面和脚本，不触碰无关模块。

## 8. 验收标准

- 四种玩法都可真实操作，不是静态展示或只有按钮的样机。
- 签池、转盘选项/模板和玩法历史刷新后仍存在；角色间数据隔离正确。
- 随机结果与动画最终停留位置一致；AI/API 不能更改随机结果。
- 角色能在开始和揭晓时自然参与；无角色时玩法独立可用；API 失败不影响抽取流程。
- 四种结果页底部逐字显示强制免责声明。
- 塔罗牌必须是竖长水晶六角牌，顶部尖角、底部斜切折角，牌背/正面/翻转全程保持此造型；78 张牌均有独立结构化牌意；不得以矩形扑克牌替代。
- 视觉遵循设计准则，无普通大卡片墙、紫蓝粉渐变、Emoji 装饰或过度空白。
- 在 375–430px 手机视口和桌面壳验证触摸、滚动、返回、键盘、动画、牌面可读性和结果展示。
- 为保存逻辑、随机逻辑、角色隔离、免责声明、塔罗六角水晶轮廓建立自动化测试或静态契约测试。
- 运行 `npm ci`、`npm run build` 和相关测试，并准确报告结果。`npm run lint` 当前不是有效 lint 检查，不能当作测试通过证明。
- PR 包含本功能需要的文件，并提供首页、抽签、转盘、塔罗牌背、塔罗翻面/牌阵、今日运势的手机视口截图。不得包含真实聊天或私人数据。
