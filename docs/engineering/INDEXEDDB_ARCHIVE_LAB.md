# DATA-006 phase A — IndexedDB archive laboratory

Date: 2026-11-25. Status: implementation candidate, **dormant, synthetic-only**.

## Boundary and registry

Proposed laboratory registry (not an active production DB): `maomao-storage-lab-*` v1, stores `records` (compound key [partition, sequence], unique byId [partition, id]) and `partitions` (keyPath partition). Loading the module opens no DB; only explicit lab factory/name/authorizer options can open it. No app page, SW, production storage key, existing repository, media store, or cloud service is changed. Do not add this laboratory name pattern to active user backup scanning. Before any production activation, review one authoritative database registry and integrate both export and restore including every new store, counts, references, failures, and rollback (DATA-001/002/005).

Partition = JSON tuple of authenticated account ID, role/group kind, conversation ID, lifecycle generation, messages/memories domain, active-lab/shadow lane. Scope is copied and frozen. Every operation requires an explicitly supplied trusted authorizer; shadow reads require shadow permission. This is local repository scoping, NOT a server authorization boundary, not a guarantee against arbitrary same-origin scripts, and not a way to infer owner identity from legacy data. No identity assignment from nicknames. No integration until current account/role generation and source permissions are trustworthy.

## Implemented interfaces

- open({name,indexedDB,keyRange,authorize}): explicit lab only; close on versionchange.
- bind(scope): immutable capability; append([{id,payload}]), page({limit,before,shadow}), get(id,{shadow}), copyLegacySnapshot(raw,cryptoProvider).
- append batches max 200 and 8 MiB estimated UTF-16 payload bytes; page default 40/max 100, uses range cursor, returns newest-first and exclusive nextBefore. Exact ID + payload replay is idempotent; conflicting payload aborts batch. Metadata and record writes share one readwrite transaction. Promise success waits for transaction complete, not individual request success. Scope rechecked before operations and result release; a post-commit permission revocation can reject acknowledgment but does not undo an already committed correctly scoped write; retry uses the same ID.
- JSON-only message payload; existing unknown fields retained, unsupported objects/values rejected. No arbitrary total record cap, no auto-eviction. No delete/edit/tombstone APIs yet; do not expose this as live authoritative repository until those semantics and stable source IDs are designed.
- Shadow copies original JSON snapshot (caller owns immutable snapshot and proves ownership); SHA-256 binds exact snapshot bytes, each bounded batch updates its checkpoint atomically. Sequence-derived staging IDs preserve duplicate/missing legacy mids as payloads; same snapshot resumes, changed snapshot fails closed. Re-verification compares each record and sequence and final count before verified-shadow; active:false always. Legacy source never modified, shadow never becomes authoritative. Legacy raw parsing and hashing remain whole-snapshot operations with 32 MiB input guard; larger/live migration needs streaming and mobile performance work. Caller must recheck source hash and account before any future cutover. No media byte migration; existing asset references only.
