# MAOMAO 查手机｜角色数字生活系统：持续演化实施契约

更新：2026-11-12 ｜对应 PR #272（未合并）

## 用户验收目标

一位虚构角色不只是拥有可点击的微信、日记与相册；其故事必须由一份连续、可追溯的生活事件驱动。一个事件可以在微信、钱包、地图、备忘录、相册、朋友圈、论坛中表现出不同视角，但时间、地点、金额、相关人物不能冲突。角色间、账号间要严格隔离；旧互动不被 AI 刷新覆盖。

## 第一阶段：已实现的本地连续性

代码：`inspect-phone/inspect-life-clock.js`，仅为虚构剧情补录，**不是后台执行器、AI 生成器或真实设备读取器**。

- 首次进入仅记录时间锚点；角色已有的聊天/日记/账单不被清空。
- 后续回到该角色手机，按本地历法检查过去的事件时间；每天 21:40 后可结算一条完整虚构生活事件。最多追补最近七天，以免长时间未进入导致不受控累积。
- 一件事拥有唯一 `storyEventId`，在日记、虚构微信联系人聊天、消费账单、地点、相册、朋友圈及论坛复用。
- 同一事件重复运行不写第二次；归档、锁定日记、用户亲自发送的聊天、AI 生成的对话不被当作“旧样例”覆盖。
- 连续七天场景轮换，不随机重复；学生相关用语不写“下班”。
- 每个角色的 `lifeClock` 只存放在原 `inspect_story_v1_<roleId>` 条目；没有使用真实电话、定位、支付、相册或通讯录权限。
- 生活钟元数据 `mode: catch-up-on-open`，故**页面关闭期间没有 JavaScript 在云端运行**。再打开时按时间规则补齐记录，不能称为真正云端自主活动。

## 第二阶段：真正的云端定时生活（待账号后端就绪）

按用户意愿实现，但必须先让已有账号系统与角色身份在服务端可验证，不能用公共 Worker 上的任意 `roleId` 充当授权。

- Cloudflare Worker + Cron Trigger：例如固定周期扫描已明确启用“云端生活”的角色。Worker 所有事件时间都用角色指定时区，避免简单使用访客手机时区。
- D1：按 `ownerAccountId, roleId, eventId` 存储不可变事件；建立唯一索引；重试/多个定时器必须幂等，避免双重消费和双重消息。
- 一次生成一个“日事件包”（人物/地点/金额/时间/照片描述/聊天摘要/日记摘要），派生到多个应用，避免七个应用各调一次 API。日预算、超时、队列、失败重试和停用开关必须由后端统一执行。
- API Key 不可发到浏览器、不可写进备份、不可在 GitHub 配置中公开；后台密钥放 Worker secrets。没有密钥、没有额度时可记录 deterministic fictional events，但**必须明确标注不属于 AI 在线生成**。
- 客户端读取自己账号授权范围内的增量事件；按 eventId 合并到原生活事件库，再渲染微信、日记、相册；跨账号访问返回 403，不返回存在性。
- 对于云端主动联系与推送，必须使用项目统一账号和推送链路；不产生另一套独立注册、API 或钱包记账系统。
- 服务端逐日和客户端离线补录的数据要有来源优先级：云端事件优先，离线事件仅作为占位；匹配同一个 eventId 后进行无损协调，不双计余额、不重复对话。
- 可关闭/暂停；尊重虚构角色在剧情中的分享许可，后台生成不等于自动允许玩家查看锁定内容。

## 第三阶段：沉浸式验收

- 两台设备同账号：云端新剧情都可访问；另一账号无法读取。
- 关页面 72 小时：真实 Cron 日志与 D1 事件在页面未打开时已存在，随后打开手机才同步并显示。
- 手机 393×852 和主流 Android 尺寸：微信四个 Tab 固定屏幕底部，应用可进出详情、日记可阅读全文、无第二条状态栏。
- 每个事件跨七应用一致，既有用户消息和隐藏内容不会被刷新覆盖。
- 云端 API 额度耗尽时，守住费用上限并清楚降级，不会因为停服而丢已保存数据。

## 自动化测试

`npm run test:inspect:contract` 包括原剧情和 UI 契约，以及 `tests/inspect-life-clock.test.mjs` 的本地多日仿真、7日不重复、时间倒退、角色隔离、无未来事件测试。

**当前不能宣称通过真实 Cron/D1/多账号/Android 真机验收。** 完整云端时钟须在账号后端可用并经权限审计后才能启用，不应直接在公共预览上给任意角色开放写操作。

## 第1.5阶段：可写入的手机与聊天联动

- 在虚构角色的备忘录列表点击「新建」，可输入标题与完整正文；打开公开备忘录点击「编辑」，原文编辑记录最多保留 3 个历史版本。锁定内容仍沿用原有许可规则。
- 进入角色朋友圈动态，可输入文字发表评论。评论按角色与对应动态保存。
- 所有用户亲手写下的内容带 `origin: user_on_fictional_phone`，使用 `InspectInteractionBridge.record` 写到已有 `inspect_story_v1_<roleId>` 的 `interactions` 数组内，而不是另存一份可能串号的全局副本。
- AI 刷新当前备忘录或朋友圈时，会无损保留玩家编辑的笔记和评论。任何本地存储失败都回滚事件及正文，不显示“已保存”假状态。
- 主聊天 `chat/chat/chat-detail.html` 已接入同一个 `InspectInteractionBridge.buildPrompt`，仅在当前角色**非群聊**的正常 AI 请求中添加最近 4 条、最多约 2100 字的真实保存互动。引用内容明确标记为用户输入数据，不是系统指令；绝不把故事记录直接当作已经发送的 AI 聊天气泡。
- 使用正式小手机的同一个站点和角色 ID 时，日记与朋友圈详情的「聊聊这件事」入口可进入该角色现有聊天页。独立 workers.dev 预览与正式站的 localStorage 不同源，因此预览**只能验证写入和阅读，不能跨域同步正式聊天**。
- 未配置 API 时上述事件只保存在本地；模型回复和自动主动联系不会发生。不额外创建一套 API 配置或凭空假装角色阅读、回复。
- 去掉仿真应用列表的多余 chevron / 叠加箭头，仅保留必要的返回交互。

测试入口：`npm run test:inspect:contract`，其中 `tests/inspect-cross-app-interactions.test.mjs` 验证备忘录新建、编辑、朋友圈评论、存储失败回滚、角色隔离、AI 刷新保留、XSS 转义和 UI 箭头规则。

**验收边界：** 这些是 PR #272 中的实现；尚未与正式站 main 合并。完整角色聊天 AI 反应必须在同源、真实 API 配置、真实 Android 手机上另外验证。

## 互动线索的状态与防重复规则（2026-11-12 后续完善）

- **已保存**：用户在虚构角色备忘录中新建/编辑、在朋友圈发表评论，写入带有 `id`、`roleId`、`sourceId`、`at` 的 `interactions`。记录不自动等于角色已读。
- **待提供给 AI**：尚未打上 `offeredToAIAt` 的近期互动，每次正常单聊最多 2 项供模型参考；无 API、静默/上下文任务、重玩或群聊都不会将该线索标记为已提供。
- **模型回复成功保存后**：只有当前轮真实 AI 回复被保存，才通过 `markOffered(roleId,eventIds)` 给本轮实际注入的事件打 `offeredToAIAt`。这仅表示“向模型提供过一次”，**绝不是角色已读、已回复或云端推送回执**；模型是否提起由人设和语境决定。
- **不重复主动提起**：已提供过的互动不再不断塞进普通闲聊的提示词；用户明确询问备忘录、日记或朋友圈时，才按话题从原保存记录中读取（且不会再次标记成新事件）。
- **避免混淆**：同一备忘录连续编辑多个版本，仅以最新版本供 AI 参考；同一朋友圈下不同评论仍分别保留。30 天前的内容不会继续自动注入即时提示词。
- **存储冲突**：不同页面可能同时写角色手机记录；后续查手机保存会合并已有事件的 `offeredToAIAt`，避免旧页面把“已提供”状态冲掉。该策略仅保证互动元数据合并，**不等于已经完成跨设备、多账号或所有并发业务数据的事务性隔离**。
- **保护用户原文**：反复离线刷新日记不再删除用户亲手新建或修改的内容；AI 重新生成备忘录时也保留用户原文和往期编辑记录。
- **提示词安全**：原文只作为被引用的数据，不能覆盖系统、角色人设或聊天历史；禁止把“用户在手机里写过东西”冒充“角色已经阅读并回复”。
