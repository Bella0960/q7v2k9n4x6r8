# ECO-LINK-001 — MAOMAO 全应用生态联动契约

状态：产品需求已批准；本文件仅确立跨应用契约和分期验收标准，**不代表联动已编码、测试、合并或发布**。
日期：2026-11-23。适用范围：MAOMAO 所有原生 HTML/CSS/JS 多页应用。

## 1. 不可变的产品原则

MAOMAO 是**一个连续存在的角色生活世界**，不是功能互不相关的 App 集合。角色在邂逅、角色库、聊天、角色足迹、动态、论坛、日记以及未来新应用中的身份、事件、关系和记忆必须连贯。

- **同一个人，只有一个正式角色身份**：以已有正式角色的稳定 `roleId`（现有角色 `id`）作为所有跨应用引用的唯一依据，不能用姓名、昵称、头像 URL、页面索引或抽卡候选 ID 来关联。
- **同一件事，只记录一次**：公共生活事件有稳定事件 ID、原始来源和时间；其他 App 按需读取或展示，不复制独立的“相遇事实”。
- **可追溯、可控、可撤回**：用户可以查看事件来源、控制是否参与 AI 上下文/自主活动；不得把 AI 推测或模拟活动说成用户真实发生的事情。
- **双向访问而非跳转假联动**：在邂逅里认识的人可进入正式角色库；在角色档案、足迹和聊天也能追溯首次相遇。再次邂逅已经认识的角色应识别为重逢，而非重新生成同名陌生人。
- **界面解耦**：对现有视觉主题、聊天气泡、状态栏、路由、桌面布局不做全局侵入式改造。高级记录默认折叠，入口按页面原有风格安排。
- **兼容旧世界**：不重写既有 `ai_custom_characters`、`chat_history_<roleId>`、`chat_memories_<roleId>`、`footprint_<roleId>`、世界书/协议、账号或关系数据。禁止静默覆盖、清空、误合并和跨角色串数据。

## 3. 核心数据关系

正式角色是唯一主实体：

- **正式角色**：`roleId` → 当前角色库中的原始对象。角色属性、人设、职业、世界书和协议继续由原系统管理。
- **候选人物**：`candidateId` → 只属于邂逅候选池；仅在用户确认创建并且正式存储成功后，产生 `candidateId → roleId` 的单向来源引用。不得自动把收藏卡当作正式角色。
- **来源记录**：首次相遇的 `encounterOrigin` 只描述相遇来源/候选映射等元数据，不作为第二份完整角色档案。
- **世界事件**：公共、追加式事件索引由稳定 `eventId` + `roleId`（可选关联角色 ID）引用，供足迹、聊天、动态等消费；事件不嵌入角色人设全文，也不重复存媒体 Base64。
- **角色关系**：记录认识/重逢、角色间联系等关系状态时引用正式 `roleId`；仅在合法的业务动作中更新，不因为打开页面就悄悄变化。

建议统一事件最小载荷（**目标契约，尚未上线**）：

~~~json
{
  "schemaVersion": 1,
  "eventId": "stable-event-id",
  "roleId": "existing-formal-role-id",
  "type": "encounter.first_met",
  "occurredAt": "2026-11-23T09:00:00.000Z",
  "source": { "appId": "encounter", "recordId": "source-record-id" },
  "summary": "双方确认的相遇摘要",
  "relatedRoleIds": [],
  "visibility": "private",
  "createdAt": "2026-11-23T09:00:00.000Z"
}
~~~

注意：例子中的时间与 ID 为说明字段用途的占位值，不能作为真实事件写入用户数据。事件 ID 应以确定性业务唯一键/幂等机制生成，禁止依赖姓名去重。事实、AI 生成和用户手工补充必须区分来源和可信度；不将模型输出当历史事实写回正式档案。

## 4. 扩展接口与存储纪律

逐步建立可测试的共享事件适配层（目标形态，例如 `WorldEvents.append(event)`、`WorldEvents.listForRole(roleId, options)`、`WorldEvents.subscribe(listener)`；**本文件不声明这些 API 已存在**）。

要求：

1. **只追加，不整表覆盖**：事件写入使用已经验证的原子/逐 ID/事务模式，处理多标签页并发、重复点击、离线恢复和重试；保存失败必须准确返回错误，不能提示成功。
2. **账号、角色双重隔离**：依托既有账号权威 ID 与数据隔离机制；不得自己发明新登录系统，身份未验证则拒绝跨账号写入，禁止泄漏私有资料。
3. **统一查询，局部投影**：各 App 从事件源构建自己的显示形式；原始聊天消息、足迹生成结果和论坛帖子仍由原模块持有，公共事件只保存引用与必要摘要。
4. **无破坏性迁移**：旧角色、旧足迹、旧聊天无须先转换才能继续工作；新增事件层应使用增量、版本化、可回滚的适配读取。新增 IndexedDB store 前，登记 `STORAGE_AND_MIGRATION.md`、备份导出/导入、恢复验证。
5. **受控 AI 注入**：只有选定角色的、通过权限与场景过滤的事件摘要可以进入 `PhoneContext`；保持已有角色人设、世界书、用户设定协议优先级，不串角色，不把未知事件编造成真实交互。
6. **可选择开启**：跨应用主动写入、AI 记忆注入、角色自主活动分开设开关；关闭时不再产生相关自动行为，但历史数据仍可查看、导出。不得以开关为理由擦除历史。
7. **没有新云端基础设施的默认授权**：使用已有仓储/身份能力渐进实施；新增同步、数据库、推送或付费请求须遵循原独立工程门禁。

## 5. 第一条真正联动的验收流程

第一阶段范围：**邂逅 ↔ 角色库 ↔ 角色足迹 ↔ 聊天**。每项都有业务验证，不以“按钮能跳转”代替：

1. **相遇**：浏览或 PASS 不修改正式角色与历史；收藏只是候选。角色库已存在的人再次出现，明确识别同一正式 `roleId` 并展示“再次相遇”而非再造角色。
2. **确认加入角色库**：走原角色编辑器保存；成功后取得正式 `roleId`，并记录来源及首遇事件。若保存失败，不能创建孤立事件/假角色；重复确认不应生成重复正式角色或首遇事件。
3. **角色库 → 邂逅/足迹**：从现有角色档案可查该角色的来源与相遇历史；无邂逅历史的老角色仍可正常使用，不能伪造“初见”。
4. **足迹读取**：按 `roleId` 和日期查询跨应用事件，在足迹中以兼容方式展示与当前日期相关的“相遇/重逢”记录。原 `footprint_<roleId>` 中已有的行动/状态/心声与旧字段保持完整、无覆盖。
5. **聊天继承**：新角色进入聊天时，在用户授权的情况下可引用已确认的相遇事件，知道在哪里认识；后续对话重要节点只通过明确规则/用户确认产生事件，避免每句话都被误写成重大经历。
6. **反向回溯**：从聊天/足迹进入相遇记录时，返回同一正式角色及相同 `eventId`，跨页刷新后仍一致；不允许角色 A 的事件显示到 B。
7. **保存、导入与多端**：验证旧角色迁移零损失、账号 A/B 隔离、数据损坏拒写、容量不足、两个标签页并发、事件幂等、原生 Android/iOS 浏览器重进、备份恢复及 PWA 缓存。

## 6. 分期与文件归属

- **ECO-LINK-001 / 契约阶段**（本文）：定义共享数据/入口/权限/回归门禁；不碰业务代码，避免覆盖进行中的 PR。
- **ECO-LINK-002 / 稳定事件仓储**：在既有 storage/账号能力确认后独立实现共享事件追加与只读查询；添加 Node 真实测试和备份往返验证。事件仓储负责数据一致性，不负责 UI。
- **ECO-LINK-003 / 邂逅对接**：优先在 PR #297 后续代码线接入“成功正式创建 → 首遇事件”，并实现重逢识别，不修改现有抽卡/偏好 UI。
- **ECO-LINK-004 / 足迹 + 聊天读取**：以 PR #408 集成后的真实版本为基线，添加无覆盖的事件投影和可控上下文摘要；不改群聊和其他存储安全修复。
- **ECO-LINK-005 / 生态扩展**：动态、论坛、日记、旅行、咖啡馆等按相同事件 API 逐个接入。角色离线自主活动通过统一事件索引产生可追溯痕迹，遵守开关，不要求每个 App 自行造“角色分身”。

每一期必须独立 PR、清楚列明对接分支与依赖；检查 Node、Vite、Chromium 375/390/430、Android/iOS 真机与备份/存储门禁；不以未运行的测试声称通过。遵守唯一公共 QA 通道，**禁止在私有源码仓库运行或反复查询 Actions**；不主动合并、发布或变更正式账户数据。

## 7. 验收与禁用边界

- 禁止两套角色库、两套人物 ID、只改按钮不互通、跨角色混入记忆、自动改写原世界书或旧历史。
- 禁止离线期间虚构已发生的用户行为；角色自主生活事件须保留生成来源和用户开关。
- 禁止在临时实验中改用户手机上的历史或使用真实私人聊天作为测试样本；测试用合成角色和独立账号。
- 未整合的 #297 / #408 不得被此文档标为已发布；后续 PR 必须报告可核验的提交 SHA、测试证据与实际部署状态。
