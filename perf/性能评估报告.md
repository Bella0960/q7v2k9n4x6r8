|---|---|---|

## 1️⃣ 聊天记录很长时，页面滑动是否卡顿？

### 结论：**不会**。滑动是健康的，问题在别处。

滚动帧耗时实测（4× 降频，模拟中端手机）：

| 消息数 | DOM 节点 | 滚动 fps | p50 | p95 | 最大帧 |
|---|---|---|---|---|---|
| 50 | 301 | 60.0 | 16.7ms | 17.0ms | 17.3ms |
| 500 | 3001 | 60.0 | 16.7ms | 17.1ms | 17.4ms |
| 1000 | 6001 | 58.4 | 16.7ms | 17.1ms | 33.4ms |
| 2000 | 12001 | 56.8 | 16.7ms | 17.0ms | 66.5ms |

p95 从 50 条到 2000 条**几乎不变**（17.0 → 17.0ms）。原因：滚动由浏览器合成器线程处理，气泡是简单文本节点，Chrome 扛得住 12000 个节点。

> ⚠️ 测试局限说明：这是程序化匀速滚动，非真实触摸惯性滚动（fling）。真机 fling 会额外触发更多区域的光栅化，实际手感可能略差于本数据。

### 真正的卡顿在哪：全量重渲染

`renderAllMessages()` 在 **20 处**被调用，其中第 4755 行位于**流式回复收尾路径** —— 意味着**每收到一条 AI 回复，整个会话被推倒重建一次**：

```js
function renderAllMessages() {
    chatMessages.innerHTML = `<div class="message-time">Just now</div>`;  // ① 摧毁全部 DOM
    const list = loadMessages();                                          // ② JSON.parse 全量历史
    list.forEach(m => { ... stripInternalReasoning(...) });               // ③ 逐条跑正则
    const frag = document.createDocumentFragment();
    visibleList.forEach((m, i) => appendMessageToDOM(m, i, frag));        // ④ 从零重建所有节点
    chatMessages.appendChild(frag);
    chatMessages.scrollTop = chatMessages.scrollHeight;                   // ⑤ 强制布局
}
```

实测耗时（取 3 次中位数）：

| 消息数 | 桌面 (1×) | 中端手机 (4×) | 感知 |
|---|---|---|---|
| 50 | 6.0 ms | 36 ms | ✅ 无感 |
| 200 | 22.4 ms | **134 ms** | ❌ 可感知卡顿 |
| 500 | 55.6 ms | **345 ms** | ❌ 明显冻结 |
| 1000 | 119.8 ms | **688 ms** | ❌ 长时间冻结 |
| 2000 | 220.4 ms | **1362 ms** | ❌ 冻结 1.4 秒 |

**复杂度：近似线性 O(N)** —— 消息量 40×，耗时 37.8×。这意味着只要对话继续增长，问题会无上限恶化。

### 放大效应：`getMyAvatar()` 的重复 IO

第 3173 行，`appendMessageToDOM` 对**每一条自己发的消息**都执行一次：

```js
fillAvatar(avatar, getMyAvatar(), USER_SVG);

function getMyAvatar() {
    const raw = localStorage.getItem('myProfile');   // 同步阻塞读
    const parsed = JSON.parse(raw);                   // 解析含 60KB base64 头像
    return parsed.avatar;
}
```

1000 条消息 = 500 次调用 = **135.7ms 纯浪费**（4× 降频），占重渲染总耗时的 **19%**。

## 2️⃣ AI 流式接口的响应延迟优化

这一层要拆成**网络侧**（首字延迟 TTFT）和**本地侧**（渲染掉帧）两件事。

### 2.1 网络侧：93% 的请求体是「每轮重发的稳定前缀」

拦截 `fetch` 实测真实请求体：

| 场景 | 请求体 | system prompt | 历史 | 估算 tokens |
|---|---|---|---|---|
| 轻量（无人设/记忆/世界书） | 16.1 KB | 4,884 字 | 20 条 / 797 字 | ≈ 3,787 |
| 中度 | 21.6 KB | 6,842 字 | 20 条 / 797 字 | ≈ 5,093 |
| 重度（300 记忆 + 40 世界书条目） | 30.4 KB | 9,958 字 | 20 条 / 797 字 | ≈ 7,170 |

**关键发现**：

1. **历史窗口已正确限制在 20 条**（`ChatContextPolicy.selectRecentHistory`），不是膨胀源 —— 这块设计是对的，不用改。
2. **贴纸消息被转成语义文本**（`[用户发送了一张表情包...]`），base64 不会混入载荷 —— 也对。
3. **93% 的载荷是每轮原样重发的 system prompt**。人设 + 记忆 + 世界书被 `CTX_CAP` 限在 9,958 字，控制住了，但**每一轮都要重新 prefill 这一万字符**。

#### → 优化建议：启用 Prompt Caching（最大杠杆）

system prompt 在连续对话中是**逐轮稳定的前缀**，这正是 prompt caching 的理想场景：

- **DeepSeek**：默认开启「上下文硬盘缓存」，命中后 prefill 价格降至约 1/10，且显著降低 TTFT
- **OpenAI / 智谱 / Moonshot**：均支持 prefix caching，要求前缀逐字节一致

落地要点：
- 把**稳定的部分（人设 / 世界书 / RP 协议 / 长期记忆）放在 system prompt 前部**，把**易变的（时间、近期历史）放后面** —— 否则缓存整段失效
- 当前 `PhoneContext` 的组装顺序需要检查：如果时间戳或动态数据插在了人设前面，缓存会 100% miss
- 重度场景下 7,170 tokens 的 prefill，命中缓存后 TTFT 通常可改善 30~60%（取决于服务商）

#### → 次级建议

- **连接复用**：`fetch` 默认 keep-alive，但可考虑对 API 域名加 `<link rel="preconnect">` 提前建连（跨地域 API 可省 100~300ms 的 DNS+TLS）
- **超时策略已合理**：三段式超时（连接 15s / 无数据看门狗 30s / 总上限 120s）设计正确，无需调整
- **rAF 渲染节流已实现**：`phone_stream.js` 已把高频 delta 合并到每帧一次，这块写得很好

### 2.2 本地侧：流式期间每帧强制布局 ∝ 节点数

`paintStreamLive()` 每帧执行：

```js
streamBubble.textContent = tmpText;                    // 写：弄脏布局
chatMessages.scrollTop = chatMessages.scrollHeight;     // 读：强制同步重排
```

实测每帧成本（4× 降频）：

| 消息数 | DOM 节点 | 每帧布局成本 | 是否超 16.7ms 预算 |
|---|---|---|---|
| 30 | 211 | 1.30 ms | ✅ |
| 60 | 421 | 1.46 ms | ✅ |
| 120 | 841 | 1.70 ms | ✅ |
| 250 | 1751 | 3.19 ms | ✅ |
| 500 | 3501 | 8.57 ms | ⚠️ 吃紧 |
| 1000 | 7001 | 12.82 ms | ⚠️ 吃紧 |
| 2000 | 14001 | **24.77 ms** | ❌ **超预算，必然掉帧** |

#### ⚠️ 两个被数据推翻的假设（重要）

我最初假设的优化方向，实测后**不成立**，记录在此避免返工：

| 假设 | 实测结果 | 结论 |
|---|---|---|
| 「每帧跑全量正则是 O(n²)，很贵」 | 全文重洗 1.6ms vs 增量 1.0ms（整个流式周期） | ❌ 可忽略，不值得优化 |
| 「去掉 `scrollHeight` 读取就能消除 layout thrashing」 | 现状 8.58ms/帧 → 改后 8.33ms/帧（**1.1×**） | ❌ **无效**。因为写 `scrollTop` 本身就要强制布局 |
| 「`content-visibility` 能解决流式卡顿」 | 8.58 → 8.12 ms/帧（**仅 5%**） | ❌ 收益微小。它仍需对 1000 个元素做可见性判定，仍是 O(N) |

**真正的根因**：只要有 N 个布局节点，内容一变就要重排 N 个。除非把节点**从 DOM 里彻底移除**，否则无解。

| Fix A　`content-visibility` | 339.3 ms | **49%** | 1 行 CSS |

### 🟢 Phase 1：低成本速效（建议本周做，合计 76% 提升）

#### Fix A：`content-visibility` —— 一行 CSS 拿 49%

```css
/* 屏幕外的气泡跳过渲染（布局 + 绘制），自动按视口判定 */
.msg-row {
  content-visibility: auto;
  contain-intrinsic-size: auto 76px;  /* auto 会记住真实高度，减少滚动跳动 */
}
```

**注意**：`contain-intrinsic-size` 的初始值（76px）要和气泡平均高度接近，否则首次渲染时滚动条长度会抖。`auto` 关键字让浏览器记住已渲染过的真实尺寸，二次进入时不再抖。

#### Fix B：头像缓存 —— 消除 19% 的纯浪费

```js
let _myAvatarCache = null;
function getMyAvatar() {
    if (_myAvatarCache !== null) return _myAvatarCache;
    try {
        const raw = localStorage.getItem('myProfile');
        if (raw) {
            const parsed = JSON.parse(raw);
            if (parsed && parsed.avatar) { _myAvatarCache = parsed.avatar; return _myAvatarCache; }
        }
    } catch (e) {}
    _myAvatarCache = '';
    return _myAvatarCache;
}

// 资料在其他页面被修改时失效（MPA 架构下跨页同步）
window.addEventListener('storage', function (e) {
    if (e.key === 'myProfile') _myAvatarCache = null;
});
```

#### Fix B+：自动滚动门控（UX 修复，顺手做）

当前流式期间**每帧无条件拉回底部**，用户想往上翻看历史时会被强行拽回。加个判定：

```js
function isNearBottom(el, threshold = 80) {
    return el.scrollHeight - el.scrollTop - el.clientHeight < threshold;
}

function paintStreamLive(text) {
    // ... 原有清洗逻辑 ...
    const shouldFollow = isNearBottom(chatMessages);   // 先判定
    if (streamBubble) streamBubble.textContent = tmpText;
    if (shouldFollow) chatMessages.scrollTop = chatMessages.scrollHeight;
}
```

> 注意：这个改动**不降低**每帧成本（实测已证明读写顺序无关），它解决的是体验问题。

### 🟡 Phase 2：架构级修复（收益最大，3333×）

#### Fix C：增量追加替代全量重渲染

当前每条 AI 回复后重建整个列表。改为只渲染新增的那一条：

```js
// 现状（chat-detail.html:4755）
renderAllMessages();

// 改为：移除临时气泡后，只追加新消息的最终形态
function appendNewMessage(aiMsg) {
    if (streamBubble) {
        const tempRow = streamBubble.closest('.msg-row');
        if (tempRow) tempRow.remove();
    }
    // 用与全量渲染一致的可见性过滤，算出正确的可见索引
    const visibleList = historyList.filter(m =>
        !window.ChatMessagePolicy.isHiddenFromOnlineTimeline(m)
    );
    appendMessageToDOM(aiMsg, visibleList.length, chatMessages);
}
```

**⚠️ 实施风险（必须处理，否则会出现微妙 bug）**：

1. **`data-idx` 必须正确**：全量渲染时索引来自 `visibleList`（过滤后的），不是 `historyList`。直接用 `historyList.length` 会导致「搜索跳转定位」（`hl=` 参数）和长按菜单取错消息。
2. **为什么当初用全量重渲染**：新消息要走 `parseReplyContent` 生成思维链块 / 旁白块 / 多气泡。好消息是 `appendMessageToDOM` 内部已经调用了这个解析路径，所以增量追加能拿到同样的渲染效果。
3. **保留全量渲染作为兜底**：只在「收尾」这条路径改增量，其他 19 处调用点（如删除、转发、群投票）继续用全量，风险可控。

### 🔵 Phase 3：真虚拟列表（长期，解决流式掉帧）

这是**唯一**能解决「2000 条时 24.77ms/帧」的方案。content-visibility 只给 5%，因为它保留节点；虚拟列表移除节点。

**推算收益**（基于实测曲线）：

| 消息数 | 当前每帧 | 虚拟列表（窗口 60 行） | 提速 |
|---|---|---|---|
| 500 | 8.57 ms | ≈ 1.46 ms | 5.9× |
| 1000 | 12.82 ms | ≈ 1.46 ms | 8.8× |
| 2000 | 24.77 ms | ≈ 1.46 ms | **17.0×** |
| 10000 | （外推 ~120ms） | ≈ 1.46 ms | 与总量无关 |

**在无框架项目里落地的难点**（诚实评估，别低估）：

- **动态高度**：气泡高度不固定（文本长度、图片、卡片），必须实测后回填，不能简单 `index * itemHeight`
- **滚动锚定**：窗口切换时不能让视口跳动
- **与现有功能的冲突**：搜索跳转定位（`hl=` 参数要能滚到任意历史位置）、长按多选、引用回复、消息转发 —— 这些都依赖 DOM 节点存在
- **建议**：先做 Phase 1 + 2，它们已能解决 95% 的用户感知问题。虚拟列表放到确有超长对话需求的版本，且建议做成可开关，先在 500 条以上的会话启用
